## Why this mode exists

Cloud Development Mode is designed to make local iteration production-realistic without forcing every dependency to run locally.

It provides:

- **One mandatory base environment** on every project: `production`
- **Custom environments** driven by user intent (name + behavior + dependency policy)
- **Two reserved special environments** that are opt-in: `preview` and `development`
- A secure development workflow where a developer connects with a token and runs a cloud-hosted dev session while dependent services are provisioned as previews.

## Environment policy by project

### Base environment (non-negotiable)

Every project always has:

- `production`

This environment is never disabled in project configuration.

### Custom environment variants

Per project, operators can add additional environments based on core profiles:

- choose `production` (or another existing custom profile) as baseline behavior
- set a custom environment name
- keep independent runtime/deployment config
- enable/disable variant activation without deleting its configuration

This supports use cases such as region-specific production (`prod-eu`) or tenant-scoped staging-like envs (`customer-a`).

### Special environment: preview (explicit opt-in)

`preview` is not automatically active. It must be explicitly enabled per project.

When enabled, it behaves like a normal environment **plus** preview-specific controls:

- per-service dependency policy for preview runs
- explicit control over which dependencies start in preview
- shared dependency instance mode (for example: project A depends on project B and both A preview instances reuse one B preview instance)
- isolation mode switch (shared vs isolated dependency instances)

### Special environment: development (explicit opt-in)

`development` is an upcoming feature and must be explicitly enabled per project.

## Development environment concept (upcoming feature)

`development` is an **upcoming runtime mode** focused on developer productivity and realistic integration testing.

### Target behavior

1. Developer requests a dev session for a service in a project.
2. Platform issues a short-lived token scoped to:
   - project
   - service
   - developer identity
   - session TTL
3. Developer client connects to the platform using that token.
4. Local tooling (docker wrapper / docker utility layer) requests runtime on cloud infrastructure.
5. Platform starts the selected service in cloud dev mode while preserving local-machine workflow semantics.
6. Platform provisions dependent services and links them into the user session.
7. Per-service execution-location rules decide whether each dependency runs local, cloud, or managed dependency-mode.
8. User sees local project flow as if services were local, while execution can be distributed.
9. Session ends by explicit stop or TTL expiry, and temporary resources are cleaned.

## Token model

### Token requirements

- Ephemeral token (short TTL)
- Single-session use
- Revocable at any time
- Scope claims:
  - `projectId`
  - `serviceId`
  - `developerId`
  - `expiresAt`
  - optional `allowedCommands`

### Security controls

- Never store plaintext token in persistent DB logs.
- Redact token in UI and server logs.
- Require mutual binding between token subject and authenticated user session.
- Rotate tunnel/session credentials per run.

## Dependency behavior in development mode

When a development session starts:

- Required dependencies must resolve first.
- Optional dependencies can be skipped with warnings.
- Dependencies can be started in shared or isolated mode based on project policy.
- Shared env keys are projected from the active project environment policy.
- Service-level rules can force execution local or cloud.

### Expected outcomes

- Local developer gets a realistic end-to-end dependency graph.
- Heavy services remain remote but predictable.
- Cleanup avoids orphan preview resources.

## Suggested runtime lifecycle states

For each development session:

- `requested`
- `provisioning`
- `running`
- `degraded`
- `stopping`
- `stopped`
- `failed`

## Observability requirements

Minimum signals for each dev session:

- Session start/stop timestamps
- Provisioned dependency list
- Preview deployment IDs
- Health-check status by dependency
- Error budget and latency trend
- Cleanup result and leaked-resource counters

## Failure handling

### Common failure classes

- token invalid/expired
- dependency preview provisioning failed
- cloud dev server boot timeout
- tunnel/connectivity failure
- permission mismatch

### Recovery strategy

- Fail fast before provisioning if auth/token invalid.
- Partial rollback if dependency provisioning fails mid-flight.
- Preserve logs/diagnostics for failed sessions.
- Offer one-click retry with fresh token.

## UX expectations

The project configuration UI should expose:

- Production base environment controls
- Custom environment controls (name, base policy, enable state)
- Explicit enable toggles for `preview` and `development`
- Preview dependency-sharing and granularity controls
- Development token/session section (upcoming feature)
- Per-service development execution-location controls
- Clear explanatory text for behavior and cleanup expectations

## Rollout plan

1. **Phase 1 (current):** Configuration model + documentation + mock UX controls.
2. **Phase 2:** Token issuance + session orchestration APIs.
3. **Phase 3:** Dependency preview automation + cleanup controller.
4. **Phase 4:** Auditing, quotas, and enterprise policy controls.

## Non-goals

- Replacing production deployments with development sessions
- Long-lived shared development tokens
- Permanent preview dependencies from development sessions
