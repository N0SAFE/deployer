This document defines the full GitHub provider target for v3, consolidating what is already implemented, what is partial, and what remains to ship.

It is intentionally detailed so implementation can proceed in small, testable increments.

---

## 1) Current state snapshot (from canonical docs)

### Implemented

- GitHub source checkout baseline (`repositoryUrl`, branch/commit validation)
- Webhook ingestion entrypoints and dispatch service foundation
- PR fallback branch support (`pullRequestNumber` → `refs/pull/<n>/head`)
- Provider conformance tests for source context resolution

### Partial

- PR open/close → preview lifecycle is wired in dispatch paths but not fully end-to-end in deployment runtime
- Commit status integration exists as service pieces but is not fully chained from deployment lifecycle outcomes
- Auto-deploy from push events exists in handler logic but requires full policy + execution completeness
- Branch/tag discovery UX/API surface incomplete for deployment trigger ergonomics

### Missing (high level)

- Hardened webhook replay-window and anti-tamper guarantees
- Full deployment-rule engine (branch/path/tag filters + per-repo rules)
- First-class GitHub App installation lifecycle and repository sync controls
- Delivery diagnostics, replay tooling, and operator-grade observability
- Web control-plane coverage for GitHub provider settings and event history

## 2) Complete GitHub provider feature inventory (target)

## A. App installation & credentials

- GitHub App registration and platform-level app health checks
- Per-organization installation linking (installation ID + metadata)
- Installation token acquisition/refresh strategy with expiry-aware caching
- Credential rotation workflow (private key rotation + validation)
- Permission drift detection (required scopes vs installation scopes)
- Graceful degradation when app uninstalled/suspended

## B. Repository discovery & synchronization

- Installation-scoped repository list sync (incremental + full)
- Repository metadata cache (default branch, private/public, archived state)
- Branch and tag discovery APIs for UI autocomplete
- Repository visibility filters (org/project allowlist)
- Archive/disable behavior for deleted or inaccessible repositories

## C. Webhook intake and security

- Signature verification (`X-Hub-Signature-256`) with timing-safe compare
- Replay-window protection (timestamp freshness + nonce/id dedupe)
- Delivery idempotency (`X-GitHub-Delivery`) with bounded TTL store
- Event schema validation + strict payload normalization
- Dead-letter storage for rejected/malformed payloads
- Delivery replay endpoint for controlled retries

## D. Trigger semantics

- Push trigger with branch rule evaluation
- Pull request opened/synchronize/reopened/closed handling
- Tag push trigger with semver-aware matching
- Manual dispatch event (`repository_dispatch`) support
- Workflow-run triggered deploy support (optional policy flag)

## E. Deployment rules and policy model

- Rule priority model (global → org → project → service)
- Branch include/exclude patterns
- Path filters for monorepos (changed-files based)
- Tag filters (exact, wildcard, semver channel)
- Draft PR behavior policy (ignore vs preview allowed)
- Fork PR security policy (allow/deny/limited)
- Environment routing rules (e.g., `main -> production`, `feature/* -> preview`)

## F. Preview lifecycle (GitHub-driven)

- Create preview on PR open
- Update preview on PR synchronize (new commits)
- Cleanup preview on PR close/merge
- Optional TTL fallback cleanup for orphaned previews
- Preview naming from PR metadata (`number`, `branch`, short SHA)
- Preview URL comment/postback to PR

## G. Commit status / checks feedback loop

- Pending status when deployment starts
- Success status on healthy deployment completion
- Failure status with actionable description
- Cancelled/rolled-back status semantics
- Environment URL linking in status/check output
- Optional GitHub Checks API richer summary integration

## H. Observability, audit, and operations

- Provider event taxonomy (`github.webhook.received`, `github.rule.matched`, ...)
- Correlation IDs from webhook to deployment timeline
- Delivery history query APIs (by repo/event/status/time)
- Failure reasons classification (signature fail, rule miss, trigger blocked, etc.)
- Replay tooling with dry-run mode
- Metrics: acceptance rate, replay count, deploy trigger latency, preview churn

## I. Control plane UX (web)

- GitHub provider settings page per org/project
- Installation status + permissions view
- Repo selection and rule editor UI
- Webhook delivery log viewer with payload diff/inspection
- Trigger test button (safe synthetic event)
- PR preview policy controls and status view

## J. Reliability and scale

- Backpressure strategy for webhook spikes
- Queue partitioning keys (repo/installation scoped)
- Duplicate suppression under retries and network flaps
- Retry/backoff with terminal dead-letter routing
- High-volume org support (pagination + incremental sync)

### Phase GP-1 — Security + contract hardening

3. Deterministic environment routing

### Phase GP-3 — Preview lifecycle completeness

1. PR open/sync/close full orchestration wiring
2. Comment/status feedback back to PR
3. Cleanup guarantees and drift detection

1. Delivery log + replay panel
2. Rule editor and test harness
3. Failure analytics and alerts
