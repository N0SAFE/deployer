## Objective

Migrate and upgrade to a fully operational deployment platform in v3, prioritizing runtime value over horizontal endpoint parity.

Target architecture is **config-driven automation**: deployment, preview, ordering, dependencies, and rollback should be executed from strong typed templates.

This plan follows a **vertical-slice strategy**:

1. Define the full target feature set.
2. Implement end-to-end runtime slices that deliver real deploy capability.
3. Backfill remaining module parity and hardening.

See target scope in [Platform Feature Target](/docs/deployment/platform-feature-target).

## Migration principles

1. **Migration = upgrade**, not copy/paste parity.
2. **Contracts first** (`standard.zod` builder), then API, then web domain layer/pages.
3. **No fake done**: deploy success means runtime + routing + health verified.
4. **One source of truth** for orchestration state transitions.
5. **Quality gate always green** (`bun run check`) at each phase boundary.
6. **Configuration over hardcode**: all provider and strategy variations must be represented in templates.
7. **Compile before execute**: every run must produce a deterministic execution plan from template inputs.
8. **Internal infrastructure first**: mesh routing, load balancer hardening, and cluster secret management must be production-ready before migrating deployment features that depend on them. Phases 11–12 (mesh topology + active-active LB) are treated as platform infrastructure, not optional features — migration work in Phases 4–10 assumes this infrastructure is reliable.

> **Current strategic state (2026-03-09)**: Phases 11–12 are in active hardening. All feature migration (Phases 4+) is on hold until Phase 12 is closed. This ensures that deployment routing, stream continuation, secret rotation, and trust model are solid before any user-facing migration work builds on top of them.

## Foundational architecture to migrate toward

### Config objects (versioned)

- `ProviderTemplate`
- `BuildTemplate`
- `DeployTemplate`
- `RouteTemplate`
- `PreviewTemplate`
- `DependencyTemplate`

### Compiler + orchestrator boundary

1. Config templates + runtime context are validated.
2. Compiler emits executable DAG with rollback edges.
3. Orchestrator executes DAG and emits typed lifecycle events.
4. Reconciler verifies desired vs actual state and heals drift.

## Phase-by-phase roadmap

### Phase 0 — Baseline and guardrails

**Goal**: lock down reference behavior and migration safety.

Steps:

1. Build migration inventory by module (v2 not yet in v3).
2. Identify blockers in runtime-critical modules (`orchestration`, `deployment`, `service`, `project`, `github`, `traefik`).
3. Freeze a baseline test matrix for API, contracts, and key web domain hooks.
4. Confirm docs baseline and keep this plan updated in same change sets.
5. Define template versioning and inheritance rules (global -> provider -> project -> env -> run).

Exit criteria:

- Runtime-critical missing modules are ranked by impact and dependency.
- Baseline quality gate is reproducible.

### Phase 1 — Vertical Slice A: deploy to live URL

**Goal**: a single-service GitHub branch deploy becomes truly operational.

Steps:

1. Wire orchestration queue/executor into deployment trigger path.
2. Implement template compiler for Provider + Build + Deploy + Route baseline.
3. Implement deployment phases as concrete actions:
   - source fetch
   - build
   - container run/update
   - Traefik route sync
   - health check gate
4. Persist phase transitions and emit stream events at each step.
5. Implement failure handling with clear error surfaces.
6. Add rollback to previous successful deployment.

Exit criteria:

- Triggering deployment produces a reachable URL when successful.
- Health check gating prevents false-positive success.
- Rollback path validated.
- Deployment behavior is explainable from template versions used.

### Phase 2 — Vertical Slice B: preview environments

**Goal**: PR/branch preview lifecycle is automated.

Steps:

1. Introduce `PreviewTemplate` with naming, domain, retention, and cleanup strategy.
2. Normalize preview naming and domain strategy.
3. Implement webhook-to-preview orchestration flow.
4. Add preview env variable overlays.
5. Add auto-cleanup (merge/close/TTL).
6. Add idempotency protections for repeated webhook deliveries.

Exit criteria:

- Preview created/updated from PR events.
- Preview URL becomes reachable and tracked.
- Preview teardown is automatic and auditable.

### Phase 3 — Vertical Slice C: fleet control

**Goal**: multi-service projects deploy safely with dependency order.

Steps:

1. Introduce `DependencyTemplate` and project-level dependency policies.
2. Materialize dependency graph execution from `service_dependencies`.
3. Add rollout strategies (ordered, parallel-with-constraints).
4. Add fleet-level rollback semantics.
5. Add reconciliation loop for drift (container/routing/status mismatch).
6. Add operator actions for restart/redeploy/reconcile.

Exit criteria:

- Multi-service deployment order is deterministic.
- Partial failures do not corrupt fleet state.
- Recovery operations are available and tested.

### Phase 4 — Module parity completion and hardening

**Goal**: complete remaining v2/v1 parity modules after runtime core is stable.

Priority order (default):

1. `orchestration`
2. `project` / `service` deep parity
3. `ci-cd`
4. `github` advanced flows
5. `websocket` real-time UX
6. `cleanup`, `providers`, long-tail modules

Steps:

1. Contract migration using `standard.zod` builder patterns.
2. API migration with strict controller/service/repository boundaries.
3. Web domain integration (`src/domains/<feature>/{endpoints,hooks,invalidations}.ts`) and typed routing integration.
4. Service + controller unit tests for each module.
5. Cross-module integration test updates.
6. Replace remaining hardcoded decision logic with template-driven execution.

Exit criteria:

- Module parity reached for agreed scope.
- No regression in previous vertical slices.

### Phase 5 — Production readiness

**Goal**: platform is release-safe under real operational conditions.

Steps:

1. Add integration/e2e scenarios:
   - first deploy
   - failed deploy + rollback
   - preview create/update/delete
   - fleet rolling deploy
2. Add observability SLO checks (latency, failure reason quality, stream completeness).
3. Validate security posture (auth guards, ownership checks, secret handling).
4. Document runbooks (incident, rollback, stuck deployment recovery).
5. Add simulation mode and policy-gate checks in CI for configuration changes.

Exit criteria:

- Release checklist passes.
- Known failure modes have documented operational procedures.

## Dependency map and parallel workstreams

### Hard dependencies (must happen in order)

1. `Template schemas` -> `Template inheritance` -> `Compiler` -> `Orchestrator` -> `Deploy MVP`
2. `Deploy MVP` -> `Preview automation` -> `Fleet orchestration`
3. `Fleet orchestration` -> `Policy/Security/SLO` -> `Production GA`

### Parallelizable tracks (after compiler baseline)

- [ ] Web UX track can proceed in parallel with backend features using mocked plan snapshots.
- [ ] Provider conformance track can proceed per adapter once unified source contract is stable.
- [ ] Observability dashboards can proceed after event taxonomy is frozen.
- [ ] Policy engine implementation can proceed with read-only enforcement before blocking mode.

### Critical blocker watchlist

- [ ] Orchestration queue reliability (without this, all higher layers are unstable).
- [ ] Traefik route apply/rollback reliability (without this, deployment success is misleading).
- [ ] Secrets and auth correctness (without this, production rollout is blocked).
- [ ] Plan determinism (without this, simulation and approvals are untrustworthy).

## Module migration checklist template

Use this checklist for each migrated module:

- [ ] Contract uses `standard.zod` builder (no raw `oc.route()`)
- [ ] API handlers use `requireAuth()`
- [ ] Business logic only in service layer
- [ ] Repository layer limited to data access
- [ ] Service unit tests cover happy path + conflict + not-found + null return
- [ ] Controller tests verify ORPC handler wiring
- [ ] Web domain layer created using current pattern (`src/domains/<feature>/{endpoints,hooks,invalidations}.ts`) and consumed by UI routes/components
- [ ] Typed route files generated where UI changes are introduced
- [ ] Template-backed config exists for provider/strategy-specific behavior (no hardcoded branches)
- [ ] Compiler output can be inspected for a deployment before execution
- [ ] Docs updated in same change set
- [ ] `bun run check` passes

## Backlog hygiene rules

- [ ] Every checkbox maps to at least one test (unit, integration, e2e, or chaos).
- [ ] Every runtime behavior change includes docs + operator note in same PR.
- [ ] Every advanced idea starts in non-blocking mode before enforcement mode.
- [ ] No feature marked done without telemetry and failure diagnostics.
- [ ] No milestone promoted if blocking criteria remain open.

## Recommended execution cadence

- Keep PRs small and slice-oriented.
- Merge only green quality gates.
- Re-verify cross-module dependencies at each phase transition.

## Success definition

Migration is complete only when the platform can reliably:

1. Deploy production services automatically,
2. Control multi-service fleets safely,
3. Manage preview environments lifecycle without manual intervention,
4. Provide operator-grade observability and rollback.
