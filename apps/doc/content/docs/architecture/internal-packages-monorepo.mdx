## The two names model

- **Physical path**: where code lives (example: `packages/contracts/api`).
- **Import name**: what apps import (example: `@repo/api-contracts`).

Both are expected and intentionally different.

## Workspace structure

- `apps/*`: runtime products (`api`, `setup`, `web`, `doc`)
- `packages/contracts/*`: shared contract definitions
- `packages/utils/*`: shared runtime/tooling helpers
- `packages/nest/*`: shared NestJS pre-wired building blocks
- `packages/ui/*`: shared UI library
- `packages/configs/*`: shared lint/type/test/tooling configuration
- `packages/bin/*`: internal CLIs used by scripts

## The `packages/nest/*` family

These are pre-wired NestJS building blocks shared between the Nest apps (`api`,
`setup`). Each one follows the same split, which is what makes it reusable:

**The package owns the MECHANISM. The app owns the POLICY.**

| Package | Ships | The app supplies |
| --- | --- | --- |
| `nest-env` | env loading + validation + a typed `EnvService` | the app's Zod schema |
| `nest-schema` | drizzle table definitions + the codec registry | the encryption key + traefik builder (via `configureSchemaCodecs`) |
| `nest-database-core` | `BaseDatabaseService` over any drizzle client | the concrete database service |
| `nest-database-local` | the SQLite connection + `@Global` module | — |
| `nest-docker` | the engine client, container lifecycle, swarm-spec mapping | connection + scanner + Postgres-identity CONFIG as data |
| `nest-nodes` | node/cluster repositories | — |
| `nest-supervisor-core` | supervisor base classes + event bus | each supervisor's `buildSwarmSpec()` |
| `nest-lifecycle` | the app-lifecycle phase/event service | — |

Two consequences worth knowing before you add code:

- **No package names a platform service.** `@repo/nest-docker` knows HOW to schedule
a swarm service; the supervisor topology table (which services exist, on how many
nodes) stays in the app, because naming our ingress/redis/database is a platform
decision. The same applies to `PLATFORM_SUPERVISOR_TOPOLOGY` versus the generic
runtime vocabulary.
- **No package reads `process.env`.** Configuration arrives as data through a narrow
interface (`DockerConnectionConfig`, `ScannerConfig`, `PostgresIdentityConfig`) or
through a `forRoot({ schema })` call, so a second Nest app can use the primitives
with its own variables instead of inheriting the first app's environment contract.

When adding behaviour, ask which side of that line it falls on. Business logic that
exactly one app consumes belongs in that app, even if the package is where it would
be convenient.

## Dependency model

- Internal dependencies use workspace references (commonly `"*"`).
- Turborepo computes the task graph and rebuilds impacted dependents.
- Cross-package changes should always be validated from repository root.

## Package build & type pipeline

Every package is consumed as built output, never as raw TypeScript. One builder,
`tooling/bin-pkg-build`, drives both halves:

- **JS**: bun bundles each source file to `dist/esm/**` (ESM) and `dist/cjs/**`
  (CJS); JSX packages additionally emit `development` + `production` variants.
- **Types**: tsc (native TypeScript 7) emits declarations to `dist/types/**`,
  mirroring the source tree, with declaration maps back to `src/`.

`exports` points `types` at `dist/types/**` and `import`/`require` at the built
JS. That is what keeps a consumer's type-check to declarations instead of
re-compiling every package implementation. Turbo drives it:

| Task | What it does |
| --- | --- |
| `build` | JS + declarations (dependency order via `^build`) |
| `build:types` | declarations only (`dist/types/**`), ordered by `^build:types` |
| `watch:types` | root script: `turbo watch build:types` |
| `type-check` / `lint` | wait for dependencies' `build:types` |

Two declaration-emit rules follow from the above, both documented in
`tooling/bin-pkg-build/AGENTS.md`:

- Recursive Zod schemas must use named recursive interfaces (`z.ZodType<…>`);
  anonymous self-references are emitted as `any`.
- Values whose inferred type exceeds TypeScript's serialization limit (TS7056)
  must be split or explicitly annotated. `@repo/api-contracts` exports each
  module contract and lets each app compose the full router locally
  (`apps/api/src/core/orpc/app-contract.ts`).

## Change workflow for shared packages

1. Update the internal package API (exports/types/contracts).
2. Update dependents (`apps/*` and/or `packages/*`).
3. Validate with root checks:

```bash
bun run check
```

4. Keep docs aligned in the same change set.

<DocCallout title="Boundary reminder" tone="info">
Avoid deep imports into package internals. Prefer stable public exports from each package `exports` map.
</DocCallout>

## Common pitfalls

- Confusing import names and physical paths in docs/examples.
- Introducing app-specific behavior into shared packages without clear boundaries.
- Exporting business logic from a package when only one app needs it — keep it in
  that app and expose the shared primitive instead.
- Hard-coding one app's config (env var names, service names) inside a package
  instead of taking it as a parameter or a `forRoot` option.
- Skipping root-level validation after changing shared packages.
