## Mental model

**Two apps, one handover, and a gate between them.** Onboarding is its own process because the API is a **converged-platform process**: migrations, seed, admin creation and supervisor convergence all assume a database URL exists. Making ONE process cover both phases is what produced the gateway, the sub-app pipeline and the runtime fallback swap.

```mermaid
flowchart TB
    subgraph SETUP["apps/setup — the GATE, exits after handover"]
        S1["wizard (setup.\u007bprefix\u007ddeployer.localhost)<br/>serves the form; persists choices to node_config"]
        S2["cluster: swarm init/join + node policy"]
        S3["handover: deliver /setup/trigger\n→ poll /health/ready → retarget dynamic-api.yml\n→ rewrite dynamic-setup.yml → ready → exit"]
    end
    subgraph API["apps/api — one normal graph, started behind the gate"]
        A1["AppModule<br/>ORPC + product features + SSR views"]
        A2["/health (liveness) · /health/ready (readiness)"]
    end
    SUP["Supervisors (owner: the API)<br/>Traefik · Edge connector · Global DB · Local DB<br/>Redis · Managed web"]
    AGT["deployer-mesh-agent (per node, NOT supervised)<br/>WireGuard mesh · node doors"]
    S1 -->|persists choices| A1
    S3 -->|prod: schedules · dev: compose gates| API
    API --> SUP
    SUP -.->|"node.doors via the mesh roster"| AGT
```

- **Setup owns `setup.{prefix}deployer.localhost`; the API owns `api.{prefix}deployer.localhost`.** Traefik routes both by Host from two files, `dynamic-setup.yml` and `dynamic-api.yml`.
- **The API boots ONE graph and starts only when setup opens the gate.** There is no gateway, no sub-app pipeline, and no pre-setup mode. `main.ts` and `compile.ts` build the same `AppModule`.
- **`GET /setup/health` means “the API may start”.** It is an INPUT to the API's existence, never a report about it — which is what keeps the dependency chain a straight line: `setup → api → web`.
- **The wizard is served by SETUP, and the API executes.** Setup collects and persists; the API has the Drizzle schema, migrations and auth, so it does the provisioning. The setup contract (`/setup/*`) stays one implementation, in the API.
- **Supervisors are owned by the API**, which is why readiness only turns green after they have converged.
- **The mesh agent and its doors are not supervisors.** `deployer-mesh-agent` is a plain host-network container on every node (started by setup or the API, whichever reaches the node first); it runs the WireGuard mesh and the node's **doors** — the loopback/mesh listeners in front of Traefik — from the replicated `node.doors` setting the API publishes. See [Networking](/docs/deployment/networking).

### dev vs prod — the only difference

| | dev | prod |
|---|---|---|
| Who starts the API | **compose**, behind `depends_on: setup-dev: service_healthy` | **setup**, which schedules it as a swarm service from `DEPLOYER_API_IMAGE` |
| What setup does with it | resolves the address compose will fill in | creates the service, then watches it |
| Everything else | identical — gate, trigger delivery, retarget, exit | identical |

`SETUP_MODE` is the single behavioural branch, so the local path is a faithful rehearsal of a real deployment.

### The restart case is the same flow

If `node_config.setupState` is already `setup_done`, setup skips the wizard (there is nothing to collect), re-verifies the cluster, and opens the gate at boot. The API then provisions the **delta** — migrations and seed are idempotent — and setup hands over and exits. One code path, not two modes.

## The master access matrix

> **How to reach the platform** for every combination of **setup phase** × **ingress state**. The URLs are the same in dev and prod; `{prefix}` is `DEPLOYER_PREFIX` (empty → no segment).

| Setup phase | Traefik converged (entry port 80) | Traefik not answering (local door rescue route) |
|---|---|---|
| **Fresh boot — wizard open** (gate closed) | `http://setup.{prefix}deployer.localhost` — **the setup app**: the wizard page (served by setup; it forwards only the contract calls the API implements) | (setup is only reachable through its bootstrap Traefik, bound to loopback; there is no rescue route yet — the doors and their rescue hosts are published by the API, which is not running) |
| | `http://web.{prefix}deployer.localhost` — **not running yet**: `web-dev` gates on `api-dev` being healthy, which cannot happen before the gate opens | — |
| **Setup in progress** (gate open, API provisioning) | Same URLs; the browser's SSE stream is served by the SETUP app, which forwards the API's frames — so nothing the operator is watching crosses the ingress swap | Same as above: no rescue route until the API's ingress supervisor has published the node doors |
| **Setup complete** | `http://setup.{prefix}deployer.localhost` → the API's `/setup/done` page (the SETUP app has exited) | `setup.*` → 502 (not a rescue host) |
| | `http://api.{prefix}deployer.localhost` → API (auth + ORPC) | `http://api.{prefix}deployer.localhost` → the local door serves it straight from the API container (this machine only) |
| | `http://web.{prefix}deployer.localhost` → the real web dashboard | `http://web.{prefix}deployer.localhost` → the local door serves it straight from the web container (this machine only) |
| **Setup complete + re-provisioned** (DB wiped) | The web's setup gate re-opens the onboarding UI automatically — the operator completes it again; the wizard stops at the running state until `setup_done` |

**The rule of thumb:** the **web app is always where the human lands**. `web.{prefix}deployer.localhost` serves the web app in every phase — through Traefik, or through the local door's rescue route when Traefik does not answer, so the URL never changes; the web app itself decides whether to show onboarding or the dashboard (its setup gate). `setup.{prefix}deployer.localhost` is where onboarding RUNS (the wizard page, then the done page), and `api.{prefix}deployer.localhost` is the machine surface (health + ORPC + `openapi.json` / `reference`). No port other than the doors' entry port is ever published for the console: the rescue route lives on the loopback door, not on a host port.

**The setup hostname never disappears.** At handover, setup REWRITES `dynamic-setup.yml` to point the same host at the API's `/setup/done` page rather than deleting the router — deleting it would leave an operator who bookmarked the wizard with a Traefik 404.

## How the user gets in — onboarding flow

### Step 0 — boot pipeline (what happens before the UI)

**Setup app** (`apps/setup`, the entry point in every profile):

1. **Binds its port** (3016, internal — never published; Traefik fronts it) and publishes its own route to `dynamic-setup.yml`, so the wizard hostname is answerable from boot rather than only at handover.
2. **Opens the gate immediately if a previous run already completed** (`node_config.setupState === "setup_done"`) — nothing to collect, so there is no wizard.
3. **Founds or joins the swarm** (`ClusterOrchestratorService`, event-driven via RxJS) and applies the node policy. This must happen FIRST: the API's supervisors schedule their services onto that cluster, so it cannot be scheduled before the cluster exists.
4. **`GET /setup/health` reports 503** until the wizard's choices are persisted. That is the gate every profile starts the API behind.

**API app** (`apps/api`) — **not running yet in dev, not scheduled yet in prod:**

1. **Starts only once `setup` is healthy.** In dev compose enforces it (`depends_on: setup-dev: service_healthy`); in prod setup schedules the task.
2. **Binds `0.0.0.0:API_PORT`** and answers `/health` (liveness) immediately.
3. **`BootstrapOrchestratorService` runs on `onApplicationBootstrap`** and is the **restart path**: it only provisions when `node_config.setupState === "setup_done"`. On a fresh install it deliberately stops and logs why, because the **wizard** owns the first provisioning — the operator's credentials are in its trigger, not in the environment, and running the boot pipeline there would create an admin from `DEFAULT_ADMIN_*` defaults that nobody chose.
   - Swarm app wiring → DB probe → pending global migrations (idempotent) → default admin (policy-gated by `ADMIN_BOOTSTRAP`, default `always` because every call site is an already-configured node).
   - **No database URL yet** is NOT fatal: `/health` stays `200` and `/health/ready` stays `503`. The distinction is deliberate — breaking the PROCESS would leave nothing for onboarding to drive.
4. **Setup delivers `POST /setup/trigger`** once the API answers, which is what starts provisioning on a fresh install. Setup retries while the API is still booting, and does not retry a 4xx (a reachable API refusing the request cannot be fixed by resending it).

### Step 1 — the onboarding UI (served by the SETUP app)

The web app (compose `web-dev`, managed web, or BYO — it doesn't matter) calls `setup.getState` on boot:

- `state: "not_started"` → show onboarding.
- `state: "completed"` → show the dashboard.
- Progress mid-run → show the SSE progress stream.

Two **bootstrap strategies** are offered:

| Strategy | What it does | Supervision |
|---|---|---|
| **Local** (recommended default) | The API provisions its own Postgres 16 container via dockerode (fixed name `deployer-postgres-dev`, named volume `deployer_postgres_data`, host-assigned 5432) — OR the operator pastes an existing Postgres URL. | Provisioned container → **supervised** by `GlobalDbSupervisorService` (`mode: "managed"`). Pasted URL → `mode: "external"` (no container supervision; the guard/probe path applies). |
| **Remote** | The node joins an existing mesh (`probeMesh` reachability check, `remoteAuth` against the remote node) — the fleet pattern. | Not supervised here; mesh-level trust applies. |

### Step 2 — the provisioning pipeline (`LocalInitializationService.initialize`)

Runs as a background job with an SSE progress stream (`setup.getInitializeStream`), one step at a time:

```text
provision_database  → ensure_empty  → run_migrations  → seed_initial_data  → register_node  → finalize
```

1. **provision_database** — existing URL is probed with a real `SELECT 1` then used; otherwise the Docker Postgres container is pulled/bootstraped and its `DATABASE_URL` captured.
2. **ensure_empty** — `information_schema` table listing; 0 tables → fresh DB; existing tables → **skip migrate + seed** (idempotent re-provisioning).
3. **run_migrations** — Drizzle migrations from `config/drizzle/global/migrations`.
4. **seed_initial_data** — first admin user + default organization (from `DEFAULT_ADMIN_EMAIL` / `DEFAULT_ADMIN_PASSWORD`, or the wizard form when unset).
5. **register_node** — `node_config` finalized: `setupState: "setup_done"`, `databaseUrl`, `nodeId`, `strategy`, `databaseProvisioning: "local" | "external"`, `configuredAt`.
6. **finalize** — terminal event; `waitForSetup()` resolves.

### Step 3 — the handover

When the API reports ready, the SETUP app performs the swap, in this order:

1. **`dynamic-api.yml` is retargeted** at the API's backend. Done BEFORE waiting too, so the hostname changes BACKEND and never existence (a missing router is a 404).
2. **`POST /setup/trigger` is delivered** to the API — the operator's choices, which is what makes it provision.
3. **`/health/ready` is polled to `200`.** That is the convergence gate: nothing touches the setup hostname until the API is actually serving.
4. **`promote_ingress`** — the bootstrap Traefik releases the entry port, the swarm ingress takes it, and setup waits until the new ingress ROUTES the API (a bound port is not enough: Traefik answers a plain-text 404 until it has loaded its routes). When a dashboard was requested, setup also waits until it is routed.
5. **`dynamic-setup.yml` is rewritten** to point `setup.{prefix}deployer.localhost` at the API's `/setup/done` page.
6. **`ready` is published** — the signal this app is about to stop.
7. **The SETUP app exits** (after a short grace period for the Traefik reload and the final stream frames).

**The wizard's stream DOES cross the swap, and the wizard is built for it.** The browser reaches the wizard *through* the bootstrap Traefik, so step 4 tears the connection down. The client therefore:

- treats a closed connection as an **interruption to retry** until the whole pipeline is done — not at the API's `completed`, which arrives *before* the swap — and says so (“Connection to setup interrupted — reconnecting…”);
- is **re-synced** by the server on every reconnect: the current state of every step plus how the run ended (`completed` / `error` are remembered, because a re-sync skips history);
- sees a **failure on the stream**, not just in the phase: the step that stopped is marked failed, an `error` event carries the reason, and **Retry the failed step** re-enters the handover (`POST /setup/handover/retry`) — nothing was torn down, so it simply runs again.

### Step 4 — verification, then the button

“The pipeline reported success” is not “the operator's browser can open the platform”, so the **Continue** button is gated on two final checks (the API, and the dashboard when one was requested), each with two halves that fail independently:

| Half | Who | What it proves |
|---|---|---|
| **Routed** | the platform (`GET /setup/post-setup/verification`) | the cluster ingress routes the hostname, asked with the browser's `Host` header. Tells “up but no route yet” (Traefik's plain-text 404) from “backend failing” (5xx). |
| **Reachable** | the browser (a `no-cors` fetch of the returned URL) | DNS, the port and the network path work from where the operator sits. |

Both must pass. During the swap every check fails for a while, so a failure is a *wait* for up to 90 s, then a visible failure with **Check again** and **Continue anyway** (a browser that cannot resolve `*.deployer.localhost` is a real situation in which the platform itself is healthy). An API-only install skips the dashboard check. The checks run **after** the stream reports done and do not depend on it, so a dropped event can neither fake nor hide them.

**The API then converges its supervisors** (swarm app wiring → global DB → Redis → managed web → ingress), which is what turns `/health/ready` green and keeps it green across restarts.

### After onboarding

- The operator logs in with the seeded admin credentials.
- The web dashboard is the day-to-day surface; the **management/developer surfaces** (managed-web toggle, supervisor health, and the **Network** section — Overview / Ingress & edge / Mesh / DNS / Domains — where the lanes, the entry port, the public edge provider and mesh membership are managed) are part of the web app / health surface below.

## Supervisor state machine

Every supervisor transitions `idle → converging → converged | degraded`, emitting typed events on the shared bus (`registered`, `state-changed`, `reconciled`, `health-snapshot`):

```mermaid
stateDiagram-v2
    [*] --> idle : constructed
    idle --> pending : convergenceBlocker() returned a reason
    idle --> converging : ensureDesiredState
    pending --> converging : precondition now holds (setup created the swarm)
    pending --> pending : still blocked (idempotent — no retry storm)
    converging --> converged : reconcile ok
    converging --> degraded : reconcile threw
    converged --> converging : re-converge (port change, flag flip, event)
    degraded --> converging : retry / event / operator action
    converged --> idle : (n/a — stays registered for the process lifetime)
    degraded --> idle : (n/a)
```

### `pending` — deferred, not failed

`pending` means **the precondition for this resource does not exist yet, so convergence was never attempted**. It is deliberately distinct from `degraded` (an attempt was made and failed).

Every docker-backed supervisor is **swarm-only** (the container fallback was removed), and the swarm is created *during setup*. So before setup a swarm converge cannot succeed — it fails with `This node is not a swarm manager`, burns the retry budget and reports DEGRADED for what is really "the cluster does not exist yet". Instead:

```mermaid
sequenceDiagram
    participant S as apps/setup
    participant A as apps/api
    participant Sup as Swarm-only supervisors
    S->>S: swarm init/join + node policy
    Note over S: the cluster exists from here on
    A->>Sup: ensureAll()
    Note over Sup: engine IS an active swarm member
    Sup-->>A: converged
```

- A blocked supervisor **never calls `reconcile()`**, so it does not touch Docker, does not retry, and does not cascade (a failing Traefik used to re-trigger the old failover proxy — since replaced by the local door's rescue route — three extra times).
- Recovery is **automatic**: the API's `onApplicationBootstrap` runs the ready pipeline and then converges every supervisor. No operator click required.
- A deferred supervisor reports `healthy: false` with **zero `warnings[]`** — warnings are reserved for `degraded`.
- `managed` (compose/operator-owned) resources also need an overlay, so they defer too until the swarm exists.

| State | Meaning | Health `healthy` | What the operator should do |
|---|---|---|---|
| `idle` | Registered, never converged yet (boot window) | `false` | Nothing — it converges on the next `ensureAll` (or the shared orchestrator's bootstrap). |
| `converging` | A convergence pass is running | `false` | Nothing. |
| `converged` | Desired state matches reality | `true` | Nothing — nominal. |
| `pending` | **Deferred**: the precondition does not exist yet (e.g. swarm-only service before setup created the cluster). No attempt was made. | `false` | Nothing — it converges automatically once setup creates the swarm. Only actionable if it stays `pending` after setup. |
| `degraded` | Last reconcile threw (detail recorded) | `false` | Read `detail` + `warnings[]`; act (see [Failure matrix](#failure-matrix--recovery-playbook)). The app NEVER stops because of a degraded supervisor. |

**Reachability of “process info”:** any consumer resolves a supervisor with `await orch.getSupervisor(SupervisorClass)` and gets `getProcessInfo()` — the docker process (desired spec + live container state), URLs/entry port/connection DSNs — all Zod-validated.

## Ingress state matrix (Traefik × local door)

The ingress is **Traefik behind the node's doors**. Traefik is a swarm `global` service with no host port of its own (its routes come from the API's HTTP provider); the node's `deployer-mesh-agent` runs the doors in front of it — `127.0.0.1:<entry port>` for the local lane, `<mesh address>:<entry port>` for the private lane. The **local door carries a rescue route**: when Traefik does not answer, it serves the platform's own hostnames (`api.*`, `web.*`) straight from the API and web containers. Nothing is ever published on another interface to compensate — see [Networking](/docs/deployment/networking).

| Traefik state | Local door | Host listeners | What `api.*` / `web.*` do | Operator sees |
|---|---|---|---|---|
| **converged** | forwards everything to Traefik's `local` entrypoint | Only the doors (loopback; + mesh address with the private lane; + LAN address with "allow same-network join"). `:80`/`:443` on every node only with an acknowledged `direct` edge | Routed by Traefik on every enabled lane | Nominal app |
| **converging / task not running** (boot window, crash, image pull) | Traefik unreachable → **rescue route** | Same doors | On this machine, served straight from the API / web containers; every other hostname returns 502 until Traefik is back | Supervisor `converging` / `degraded` in `/health/detailed` |
| **degraded — inbound edge port taken** (`EntryPortConflictError`: a node already binds `:80`/`:443` for the `direct` edge; fatal → no retry) | rescue route | Doors only (the ingress service is removed) | Rescue on this machine; the public lane is down | Supervisor detail “A node already binds :80/:443”. Free the port or switch edge provider on **Network → Ingress & edge**. |
| **any** — **the door cannot bind its port** (another process holds `127.0.0.1:<entry port>`) | `failed` | No loopback listener | Unreachable from this machine through the local lane; the private and public lanes are unaffected | The door is `failed` in the doors table on **Network → Ingress & edge**; change the entry port there (or stop the other process). |
| **not started yet** (before the API has published `node.doors`) | absent | setup's bootstrap Traefik on loopback | — (onboarding phase) | The wizard |

**Why there is no “failover” host port any more:** the failover proxy this replaced published `:80`/`:3000`/`:3001` on every interface of every node whenever Traefik degraded. The rescue route keeps the console reachable on the machine itself without opening anything to the network.

## Restart matrix

“Restart” semantics — everything is **event-driven + idempotent**, so restarts converge to the same end state:

| Scenario | What happens | End state | Timeout/notes |
|---|---|---|---|
| **API container restarts** (compose restart / crash) | Gateway boots → `node_config` already has a URL → verify → migrations no-op → main app. Supervisors re-run; Traefik and the node doors reconcile to the same state. | Nominal, no wizard | Health green from second 0; full ready in a few seconds. |
| **Full stack restart** (`docker compose up -d`, same volumes) | API + web containers restart (DB volume persists). Same as API restart + web reboots against the same token/store. | Nominal | Web instance-token volume persists → no re-registration needed. |
| **Host reboot** | Docker brings back the mesh agent and containers by restart policy (`unless-stopped`); Swarm restarts its services (Traefik, managed Postgres, Redis, managed web). The mesh agent re-applies WireGuard (Swarm binds the mesh address) and re-converges the doors from its own roster copy, even before the API is back. API re-attaches to the platform network. | Nominal | First to answer: `/health`. |
| **Managed Postgres container restarts/stopped** | `GlobalDbSupervisorService` probes (`SELECT 1`, container state); if stopped it calls `startPostgresContainer()` (reuses the fixed-name container + named volume — data survives). | Nominal | Degraded only while it's actually down; converges when back. |
| **External DB restarts** | Not supervised (external mode). `DatabaseStartupGuard` + probes; app reports DB health in `/health/detailed`. | Nominal (as long as the DB returns) | No container is touched. |
| **Traefik task restarts** (crash) | Swarm reschedules the `global` task; the supervisor verifies a task is running. Routes are re-polled from the API on start. | Nominal | During the window the local door's rescue route serves `api.*` / `web.*` on this machine. |
| **Web container restarts** (dev web) | Compose restarts it; it re-registers/persists its instance token; Traefik route already points at it. | Nominal | During the window `web.*` returns Traefik's 502/404 — brief. |
| **Managed web (API-supervised) restarts** | `ManagedWebSupervisorService` sees stopped → **recreates** it (fresh app-instance token, revokes the stale one — rotation is safe, only the newest env-carrying container survives). | Nominal | No manual step. |
| **Entry port changed** (Network → Ingress & edge; the door can't bind 80) | The new port is written to the `ingress.lanes` cluster setting in the mesh roster → the API republishes `node.doors` → every node's mesh agent recreates its doors on the new port. Traefik itself is untouched. | Nominal, new entry port | The exact remediation flow for “port 80 taken”; it reaches every node, including ones the API cannot reach directly. |
| **`managed_web_app.enabled` flipped** (management console) | Flag persisted (DB wins) → managed-web supervisor converges: on → spawn container + the Traefik route resolves to it (via `PlatformWebTargetService`); off → remove container + revoke token; web route then targets the external/`DEPLOYER_WEB_TARGET` web or disappears. | Nominal | Live toggle, no restart. |
| **Database wiped / re-provisioned** | `node_config` still has the URL but the DB is empty/tables missing → `tryHealFromGlobalDb` fails → **wizard reopens** → the onboarding UI returns and the operator provisions again (migrate+seed run; existing tables skip gracefully). | Wizard → Nominal | Idempotent seeding prevents duplicates. |
| **Fresh mesh, no `ingress.lanes` yet** | The first write seeds the entry port from `DEPLOYER_TRAEFIK_HTTP_PORT` (default 80); after that the cluster setting is the only source. | Nominal (if the port is free) | If it is taken, the local door reports `failed`; change the entry port. |

## Failure matrix & recovery playbook

| Failure | Symptom | Detection (how you know) | Automatic behavior | Recovery |
|---|---|---|---|---|
| **Entry port (80) already bound on loopback** by another process | `web.*`/`api.*` unreachable from this machine through the local lane | The local door is `failed` (doors table on Network → Ingress & edge) | The agent removes the container that could not bind, so it never squats the port | Reach the console through another lane (private or public) or another member, set a **free entry port** (e.g. 8080) → every agent recreates its doors on it. |
| **`direct` edge: `:80`/`:443` already bound on a node** | Public lane down | Traefik `degraded` (`EntryPortConflictError`, fatal — the app stays up) | The ingress service is removed; the local door's rescue route keeps `api.*`/`web.*` reachable on the machine | Free the port, or switch the public lane to another edge provider. |
| **Traefik image pull fails / config invalid** | Hostname routing down | `degraded` with detail | Supervisor re-converges with backoff; the local door's rescue route covers `api.*`/`web.*` on the machine | Check `DEPLOYER_TRAEFIK_IMAGE` / the routes the API serves to Traefik's HTTP provider; retry from the dev/management page (`convergeNow`). |
| **Docker socket unavailable** at boot | Nothing supervised starts; no door can be created or recreated either (the agent drives the same engine) | Supervisors degraded on docker errors; `/health/detailed` | Backoff + degrade | Fix the socket mount; restart the API. |
| **Global DB unreachable** (external) | App fails health; wizard reopens on next boot if it can't heal | `SELECT 1` probes fail; `GlobalDbSupervisorService` degrades | Nothing retries the external URL — operators fix the DB | Restore the DB / fix the URL; restart. Onboarding stays reachable throughout, because setup does not exit until the API is green. |
| **API container keeps crashing** | Container cycles; health check fails | Compose restart policy + `/health` | Restart policy handles it | Check logs; the DB must be reachable (mandatory, even in dev). |
| **Web app container crashed** | `web.*` 502/404 during the window | Managed web supervisor degrades (container missing while flag on); dev web is compose-managed | Managed web is recreated; dev web restarts via compose | None — automatic. |
| **Managed-web token revoked** (rotation edge) | Managed web 401s | `app_instances` heartbeat/revocation | Supervisor recreates the container with a fresh token on next convergence | None — automatic. |

### The entry-port remediation walkthrough (the only “config” action ops ever needs)

```mermaid
sequenceDiagram
    participant Op as Operator (browser)
    participant Web as Web app (Network → Ingress & edge)
    participant API as API (ingress lanes)
    participant R as Mesh roster (replicated)
    participant AG as Mesh agent (every node)
    Op->>Web: reach the console through another lane or member
    Web->>Web: doors table shows the local door FAILED (port 80 taken)
    Op->>Web: set entry port = 8080
    Web->>API: update lanes (entryPort 8080)
    API->>R: write ingress.lanes, then node.doors
    R-->>AG: gossip delivers node.doors
    AG->>AG: recreate the doors bound to :8080
    Web-->>Op: door converged; api/web.* answer at :8080
```

## Health surface

| Endpoint | Auth | Includes supervisors | Purpose |
|---|---|---|---|
| `GET /health` | None | No | Docker healthcheck + startup gate — answers `200` from the first second (liveness only; it never touches the database). |
| `GET /health/detailed` | Yes (session/bearer) | Yes — `supervisors[]` with `supervisorId`, `state`, `healthy`, `detail`, `warnings[]`, `checkedAt` | Operator dashboard; the source of truth for degraded supervisors. |

Supervisors aggregate via `SupervisorOrchestratorService.getHealthOfAll()` — every probe runs a **real measurement** (HTTP probe, `SELECT 1`, container inspect) validated against the supervisor's Zod `payloadSchema`; failures never throw — they degrade into an unhealthy snapshot.
