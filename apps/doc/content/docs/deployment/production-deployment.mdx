## Deployment topology in this repository

This repository still contains compose-based production and prod-like files for local and transitional workflows.

Primary compose sets live under `docker/compose/`:

- Full stack: `docker-compose.prod.yml`
- Prod-like local workflow: `docker-compose.prod-like.yml`
- Split services:
	- API: `api/docker-compose.api.prod.yml`, `api/docker-compose.api.prod-like.yml`
	- Web: `web/docker-compose.web.prod.yml`, `web/docker-compose.web.prod-like.yml`
	- Docs: `doc/docker-compose.doc.prod.yml`, `doc/docker-compose.doc.prod-like.yml`

<DocCallout title="Production model for v3" tone="success">
The production model is Docker Swarm (manager + worker nodes), implemented behind the dockerode SDK — no independent per-node compose islands in the fleet runtime, and NO `docker stack deploy` / CLI scripts: the API converges the engine into swarm mode (SwarmBootstrapService). **Layering:** Swarm schedules the workload Deployer owns (user deployments/projects/services via the `runners/swarm` backend); Deployer's own platform services (`api`, `web`, `traefik`, DB) stay under supervisor / compose ownership — never scheduled on Swarm. Compose files remain useful for local/dev/prod-like flows. See `docs/swarm-orchestration/`.
</DocCallout>

## Production topology (Swarm manager + worker nodes) — implemented

- One Swarm cluster per environment (prod/staging/etc.).
- Manager node(s) own orchestration state and scheduling decisions.
- Worker nodes join the cluster and execute scheduled workloads; **shared-node rule**: every node runs control-plane AND user workloads (no dedicated workers).
- Control-plane services (`api`, `web`, `traefik`) are managed by the platform supervisors or Compose — NOT scheduled on Swarm. Only deployed user workloads (projects/services) become Swarm services via the `runners/swarm` backend.
- The **controlling manager is elected by the mesh** (weighted score, quorum-aware, term-guarded CAS) — the platform master, distinct from Swarm's Raft leader.
- For high availability, prefer an odd manager quorum (`3` managers) over a single manager.
- Single-node installs run the SAME code path: the API idempotently `swarm init`s the host (manager == worker) to schedule Deployer-owned workloads; the platform ingress/infra (Traefik, DB, Redis) stays supervisor/compose-managed — no manual scripts.

## Replica policy (minimum 2 when possible)

For user-facing critical services, target this rule:

- If schedulable nodes $\ge 2$, enforce replicas $\ge 2$.
- Spread replicas across nodes (`max_replicas_per_node: 1`) to avoid same-node concentration.
- Keep health checks + rolling update/rollback guardrails enabled.
- Explicitly document exceptions for singleton/stateful workloads.

## Ingress and routing model (Traefik-first)

- Traefik is the canonical ingress and load-balancing layer.
- In Swarm mode, Traefik should discover services from the Swarm provider and route via service labels.
- Standard HTTP/S traffic does **not** require a custom redirect app when Traefik + Swarm routing is correctly configured.
- There is **no standalone load balancer**: Traefik is the sole reverse proxy; the API's direct-proxy supervisor temporarily takes over ingress only while Traefik is down.

## Recommended release sequence

1. Validate env and configs.
2. Deploy/update stack from a Swarm manager node.
3. Validate service replica health and placement across nodes.
4. Validate API health and auth-critical endpoints.
5. Run smoke checks for login, routing, and core flows.

## Current repository scripts (compose/prod-like)

- Full stack production compose:
	- `bun run start`
- Prod-like local stack:
	- `bun run prod`
	- `bun run prod:down`
- Split prod-like:
	- `bun run prod:api`, `bun run prod:api:down`, `bun run prod:logs:api`
	- `bun run prod:web`, `bun run prod:web:down`, `bun run prod:logs:web`

## Environment and readiness checks

Before rollout:

```bash
bun run check-env
bun run check-env:api
bun run check-env:web
bun run check-env:doc
```

Before merge/release branch handoff:

```bash
bun run check
```

<DocCallout title="Release safety" tone="warning">
Never treat a successful container start as a complete release check. Always validate API health, web routing, auth flow, and core critical paths.
</DocCallout>

## Rollback posture

- Keep previous known-good image/tag available.
- Roll back API and web independently when possible.
- Re-run smoke tests after rollback confirmation.

## DNS and SSL setup

### SSL certificates

- **Auto Let's Encrypt** via Traefik ACME (default for all services)
- **Custom certificate upload** per domain/service for enterprise requirements

### DNS configuration

- **Platform-managed mode**: Cloudflare (first supported provider) — platform manages wildcard DNS, preview subdomains, and SSL automatically
- **Manual mode**: user configures DNS records externally, platform only manages Traefik routes

### Wildcard DNS for preview subdomains

Preview environments need a wildcard DNS record:

```
*.preview.<base-domain>  →  A/CNAME  →  <traefik-ingress-or-edge-ip>
```

Traefik handles routing to the correct preview container based on the subdomain.

### Zero-downtime deploy strategies

Configurable per service:

- **Rolling update**: new container starts, old stops after health check passes
- **Blue-green**: both versions run, Traefik route swaps atomically
- **Canary**: configurable % of traffic to new version, auto-promote if healthy
