## Overview

The v3 production baseline is a **Docker Swarm cluster** driven **entirely through the dockerode SDK** (no `docker` CLI in platform code — enforced by `scripts/check-swarm-cli-lock.sh`). The platform converges every node — including single-node dev/prod hosts — into a real Swarm cluster so the API runs ONE code path for every fleet size.

Key capabilities implemented:

- **Swarm execution backend** — user deployments run as Swarm services behind the existing `DeploymentRuntimeRunner` contract (`swarm` runner), with typed spec mappers, task-convergence health gates, Traefik swarm-provider verification, and a Compose→Swarm realizer (no `docker stack deploy` — the platform implements the transform itself).
- **Master election** — the controlling manager is elected by the mesh: weighted scoring (latency/jitter/memory/CPU/stability/quorum/hysteresis), eligibility gates, odd-quorum planning, term-guarded CAS (single winner), cooldown + `δ_master` hysteresis, and a watchdog with Suspect/grace → takeover + step-down (quorum-loss guard: never elect into a broken cluster).
- **Node sharing** — no dedicated workers: every node runs control-plane and user workloads (default role `both`; the only hard constraints are `deployer.ingress`, `deployer.tenant.*`, and infra). Platform control plane deployed via `docker/compose/docker-stack.deploy.yml` (spread preferences, `max_replicas_per_node: 1`, start-first rollback updates).
- **Fleet lifecycle** — idempotent cluster bootstrap (`swarmInit`), join tokens persisted locally (never `.env`), periodic `docker node ls` inventory with drift reconciliation, and lifecycle ops (remove/scale/rollback).
- **Cluster API** — `clusterContract` (`/cluster`): snapshot, node inventory, master view, node role/ingress label updates (authenticated).

## Developer workflow

Swarm is entirely API-driven — no CLI scripts:

- On boot, `SwarmBootstrapService` converges the engine (`swarm init`/join, idempotent, `SWARM_ENABLED`).
- Layering (per architecture): **Swarm schedules the workload Deployer owns** — user deployments/projects/services via the `runners/swarm` execution backend (per-project overlay networks + services). **Deployer's own platform infra** (ingress Traefik, DB, Redis, shared `deployer-platform` network) is managed by the platform supervisors or Compose (`MANAGED_*_ENABLED`) — never by Swarm. There is **no "platform swarm stack"**; `ensureOverlayNetwork` refuses to reuse a non-overlay (compose bridge) same-name network for a workload.
- `check:swarm:cli-lock` guards the SDK-first rule in CI.
