## What this platform is used for

This platform is a self-hosted deployment control plane for teams that want a Vercel/Render-like workflow on their own infrastructure.

For multi-instance deployments, the primary goal is to **expand deployment/runtime capacity** (more CPU, RAM, queue throughput, and concurrent stream capacity). High availability is a useful side effect, not the primary driver.

Primary usage:

- connect source providers and trigger deployments
- run services in Docker with health-gated rollout
- manage routing and TLS through Traefik
- operate branch/PR preview environments
- manage deployments, logs, and rollback from a web control plane

## Multi-server model (fleet)

Each server is an autonomous deployer instance with local runtime authority.

- A **server** owns local runtime execution and local state authority for workloads it manages.
- A **fleet** is a trusted set of connected servers.
- A **federation link** is an authenticated trust relationship between servers.

Design principle:

- **Federate control-plane metadata, not user traffic proxying.**

## Should a server be organization-level?

Short answer: **no**.

A server should be a **fleet-level infrastructure resource**, not owned by exactly one org by design.

Recommended model:

- server = fleet compute/runtime capacity unit
- org = tenant/security boundary
- allocation = policy-based mapping from org workload -> server capacity

This allows many orgs to share allowed parts of many servers while preserving strict isolation.

## Multi-org model (tenancy)

An **organization** is the tenant boundary for:

- projects/services
- users and roles
- policy and quota
- audit scope

Cross-server operations must be explicitly scoped by:

- target server
- target organization
- operation class
- time-to-live (TTL)

No implicit global privilege should be granted only because servers are linked.

## Can one organization run on multiple servers?

Yes — and this is the recommended fleet pattern for scale and resilience.

Best-practice model:

- one organization can own projects/services placed across multiple servers
- each workload still has a single **current owner server** at runtime
- mesh index resolves ownership; execution happens directly on owner server
- org policy decides placement (shared pool vs dedicated servers)

In short: **org scope is global, workload execution is local.**

## Best way to implement org-across-servers

Use a hybrid of centralized identity intent + decentralized runtime authority:

1. **Global org intent**
	- org membership, high-level policy, and placement intent are fleet-visible metadata
2. **Local execution authority**
	- each server is authoritative for workloads it currently owns
3. **Ownership index**
	- mesh stores where each resource is owned (`ownerServerUrl`, endpoint hints)
4. **Direct-to-owner execution**
	- API/stream requests resolve owner first, then connect directly
5. **Controlled replication**
	- replicate control metadata (ownership, membership mapping, capabilities), not full tenant data mirrors

This gives predictable operations while avoiding a fragile global single runtime authority.

## Two-entity model: allocator vs tenant requester

Your proposed split is correct and recommended:

1. **Fleet Allocator (server handler)**
	- controls server inventory, health, and available capacity slices
	- enforces placement constraints and admission rules
	- decides if an org request can be scheduled and where
2. **Organization Requester (tenant side)**
	- requests workload placement/deployment
	- can only request within org quota and policy
	- never receives global fleet visibility by default

Think of it as: org asks for capacity, allocator grants a constrained placement decision.

## Workload-sharing goal with strict visibility isolation

Mesh can share workload across servers **only for allowed workload partitions**.

Visibility rule (mandatory):

- when Org A queries server workload, return only data rows/resources authorized for Org A
- hide all resources from Org B/C/... even if they run on the same server
- fleet metrics may be shown to orgs only in aggregated/sanitized form when policy allows

### Practical filtering policy

Every workload query should include both:

- `orgContext` (active org)
- `scopeFilter` (allowed resource IDs/types/environments)

And be evaluated at owner server before response.

### Data exposure levels

- **Org view**: only own projects/services/deployments/logs/capacity usage
- **Fleet view**: cross-org infra visibility, but only for fleet-authorized users
- **Mixed users** (fleet + org roles): must choose context; backend enforces context-specific projection

## Request-to-allocation flow (recommended)

1. Org user requests deployment/scale action.
2. Request is validated against org policy + quota.
3. Allocator evaluates candidate servers (capacity/health/residency/trust).
4. Allocator commits ownership selection for the workload.
5. Mesh index updates owner location.
6. Execution runs directly on selected owner server.
7. Org receives only org-scoped status/logs/metrics.

If placement cannot satisfy constraints, request is rejected with explicit policy/capacity reason.

## Mesh topology model: by organization, not only by server

For multi-tenant correctness, mesh connectivity should be modeled as **org-scoped overlays**.

That means:

- load sharing is evaluated per organization policy and workload
- the same pair of physical servers can participate in multiple logical meshes
- each organization gets its own routing/ownership/control context

Example:

- Org A and Org B both run workloads on Server 1 and Server 2
- do **not** use one shared tenant-blind mesh context
- maintain two logical overlays:
	- `mesh(org-a)` over Server 1 to Server 2
	- `mesh(org-b)` over Server 1 to Server 2

Even if the physical links are the same, authorization and workload visibility remain separated per org.

## Required implementation consequences

1. **Org-qualified mesh keys**
	- resource lookup/index keys should include `orgId`
	- ownership resolution must return owner within org scope
2. **Org-qualified control envelopes**
	- membership/control events should carry org context (or explicit global/fleet context)
3. **Org-qualified routing hints**
	- direct-owner hints must be valid only for authorized org context
4. **Org-qualified observability**
	- org users see only org-scoped topology/workload metrics
	- fleet users may see infra-wide metrics according to fleet policy

## Why this model is important

- prevents accidental cross-org metadata leakage on shared servers
- allows different placement/limits/SLOs per org on the same infrastructure
- enables one org to be highly federated while another remains local-only
- keeps future provider/fleet overlays compatible with tenant isolation

## Final architecture decisions (canonical)

This section is the definitive model for fleet + org behavior.

1. **Server is fleet-capacity first**
	- A server is an infrastructure unit; not implicitly bound to a single org forever.
2. **Org is security and policy boundary**
	- Every workload action, query, and stream is authorized in org context.
3. **Mesh overlays are org-scoped**
	- Load sharing and ownership lookup are keyed by org scope.
4. **Direct-owner execution remains mandatory**
	- Mesh discovers; owner server executes.
5. **Dual-role users are explicit bindings**
	- Same identity can hold fleet and org roles; authorization is context-specific.
6. **Bootstrap-simple, split-later lifecycle is supported**
	- Start as org-led instance, evolve to fleet allocator model without tenant rewrite.

## Bootstrap now, split later (lifecycle)

### Stage A — Org-led single-server start

- create initial organization and org admin
- optionally bind same user as local fleet admin
- run workloads locally with org-scoped authorization

### Stage B — Org-managed multi-server federation

- joining server initiates connection to existing node
- organization enables org-scoped mesh overlay across selected servers
- ownership index starts routing workloads by org + resource

### Stage C — Fleet allocator overlay (provider style)

- fleet allocator controls capacity slicing and server placement policy
- orgs request allocations/deployments inside quota boundaries
- org visibility remains strictly tenant-scoped even on shared hardware

## Minimal entities for implementation

Required conceptual entities:

- `Server` (capacity + health + runtime metadata)
- `Organization` (tenant boundary)
- `Allocation` (org access to server slice)
- `OrgMeshOverlay` (org-scoped federation context)
- `ResourceOwnership` (org-qualified owner lookup)
- `RoleBinding` (identity -> fleet/org permissions)

These entities may map to one or more tables/services, but the boundaries must remain explicit.

## Isolation requirements checklist

- hard org scoping on all workload tables and APIs
- deny-by-default cross-org reads
- per-org quotas and admission controls on shared servers
- per-org audit trace for all deployment mutations
- explicit policy for any aggregated shared-capacity signal shown to orgs

## Fleet Manager vs Organization usage

### Fleet Manager scope (platform control)

Fleet Manager (Fleet Super Admin) is about infrastructure governance:

- connect/disconnect servers
- manage federation trust links
- define cross-server policy boundaries
- observe topology/health/capacity at fleet level
- approve high-risk cross-server operations

### Organization scope (tenant operations)

Organization roles (Org Admin/Org User) are about product usage inside a tenant:

- manage org projects/services/environments
- deploy and rollback within org permissions
- manage org members/roles
- view org-scoped logs, events, and audit data

### Key separation rule

- Fleet privileges do **not** automatically grant org data access.
- Org roles do **not** automatically grant fleet infrastructure control.

Any cross-over must be explicit and auditable.

## How a Fleet Manager user can also be a user in other orgs

This is a common and valid setup.

Recommended identity model:

- one human identity (same person)
- multiple role bindings:
  - fleet-level role(s)
  - one or more org-level role(s)
- authorization is evaluated per request context:
  - fleet endpoint -> fleet role check
  - org endpoint -> org membership + org role check

Recommended access flow:

1. User authenticates once.
2. Session carries stable identity subject.
3. User selects operating context (fleet vs org, and which org).
4. System evaluates only permissions for the selected context.
5. Audit event records actor + context + target server/org + result.

## Recommended role-binding strategy

To keep security clear and maintainable:

- avoid “super role” shortcuts that bypass org checks
- use explicit bindings (`user -> fleet role`, `user -> org role`)
- require explicit org assignment for Fleet Managers who also operate inside orgs
- require re-authorization (or step-up policy) for sensitive fleet actions

## Data model guidance (for implementation)

For future schema hardening, model these concerns separately:

- **fleet identity/bindings** (fleet roles and trust admin rights)
- **org memberships** (org roles and tenant permissions)
- **cross-server ownership index** (resource -> owner server)
- **audit trail** (actor, delegation chain, org context, fleet context, correlation id)

This keeps authorization explicit and prevents accidental privilege leakage between control-plane and tenant-plane concerns.

## Example operation with dual-role user

Scenario: user Alice is both Fleet Manager and Org Admin of Org A.

1. Alice opens Fleet view: can manage server links and placement policy.
2. Alice switches to Org A view: can deploy app services for Org A.
3. Deploy request resolves owner server via mesh index.
4. Request is sent directly to owner server.
5. Owner server enforces Org A authorization again before execution.
6. Audit captures both actor identity and org context.

Result: one user, multiple scopes, zero implicit privilege crossover.

## Request routing and ownership resolution

Control-plane mesh responsibilities:

- ownership lookup
- topology/membership state
- routing hints to owner endpoints

Control-plane mesh is not responsible for:

- forwarding end-user API calls
- multiplexing long-lived user streams

After ownership lookup resolves an owner, requests go **directly** to the owner server endpoint.

## Persistent stream policy

For SSE/subscriptions and other long-lived operations:

- open one dedicated connection per subscription to the owner server
- track each connection independently
- allow per-subscription abort/cancel

Federation links are never the transport for external user stream multiplexing.

## URL-first server onboarding flow

Recommended connection sequence:

1. Local super admin enters remote server URL
2. Local server discovers remote metadata/capabilities
3. User is redirected to remote login/consent
4. Local receives callback grant and validates state/nonce
5. Local exchanges grant for scoped short-lived token
6. Local finalizes authenticated federation link

### Direction rule for real deployments

When adding a new node to an existing fleet, the **new server must initiate** the connection.

Example:

- Server 1 = existing, already working fleet node
- Server 2 = new node currently being configured

During bootstrap, use Server 2 as the initiating side:

1. Operator opens Fleet setup on **Server 2**.
2. Operator enters **Server 1** URL as remote peer.
3. Server 2 runs discovery against Server 1.
4. Operator completes consent/auth flow on Server 1.
5. Server 2 exchanges grant and finalizes link to Server 1.

Why this direction is preferred:

- bootstrap can be driven from the node that is joining
- avoids requiring pre-created inbound trust from existing nodes
- keeps onboarding repeatable for `Server N -> existing fleet`

### If Server 2 is already configured and reconnecting

Expected behavior:

- reconnect should be idempotent (no duplicate active links)
- existing link should be refreshed/resumed instead of duplicated
- scopes must not auto-expand during reconnect
- rotation/re-auth should update credentials while preserving audit trace

Security baseline:

- PKCE (`S256`)
- short-lived authorization code and exchanged token
- strict state/nonce validation
- idempotency key and replay window enforcement
- optional mTLS for stronger server-to-server trust

## How teams should run this day to day

### Day 0 (bootstrap)

- deploy first server instance
- create org boundaries and role assignments
- connect additional servers via URL-first handshake
- define placement policy (shared vs dedicated capacity)

### Day 1 (operations)

- deploy within org scope
- monitor deployment status/logs/events
- resolve owner server then route directly for remote operations
- use explicit rollback/redeploy workflows per server or per org policy

### Failure handling

- local operations continue during network partitions
- remote operations are deferred/retriable with clear operator guidance
- suspicious peer behavior triggers link quarantine and scoped revocation

## Placement strategy inputs

Use policy + runtime signals together:

- capacity and health
- region/residency constraints
- trust-domain constraints
- org isolation policy (shared vs dedicated)
- dependency locality

## Optional pattern: active-active custom load balancer architecture (no master)

> **Added**: 2026-03-02  
> **Type**: Pattern  
> **Confidence**: Partial 🔄  
> **Scope**: v3

### Summary

All nodes run the same stack and can accept traffic; no dedicated master node is required.

Use this only when you explicitly need redirect/token-based owner-aware routing beyond standard Traefik + Swarm behavior.

### Runtime topology per node

Each server runs the same components:

- `apps/api` (runtime owner for workloads it currently owns)
- Traefik ingress as the sole reverse proxy (org-aware routing; direct-proxy supervisor for Traefik downtime)
- mesh membership + ownership index consumer/producer
- metrics reporter (`cpu`, `memory`, active streams, queue depth)

### Control-plane vs data-plane

- **Control-plane**: mesh lookup, ownership index, topology, trust, hints.
- **Data-plane**: client request/stream goes directly (or proxied) to owner API endpoint.
- For long-lived streams, the load balancer keeps one client-facing stream open and relays upstream chunks.

### Enrollment and trust model (super-admin bootstrap)

Recommended model:

1. Super-admin initiates join from new node to existing node (URL-first flow).
2. A short-lived join grant authorizes enrollment.
3. Node identity is persisted (`nodeId`, public key/cert, capabilities).
4. Runtime node-to-node auth uses node identity (mTLS or signed envelopes), not user session.

This keeps onboarding simple while preserving symmetric runtime trust.

### Key management model

- Avoid one permanent global secret for all concerns.
- Use separate material:
	- **Enrollment grant key(s)** (short-lived join grants)
	- **Inter-node transport/auth key(s)** (mTLS certs or signing keys)
	- **LB route-token signing keyring** (`kid`, active + previous during rotation)

### Canonical persistence schema (recommended)

Use persistent store for durability + in-memory cache for hot path:

| Table | Purpose | Key fields |
|---|---|---|
| `cluster_nodes` | Registered node identities and status | `node_id`, `base_url`, `public_key_or_cert`, `status`, `last_seen_at`, `capabilities` |
| `cluster_join_grants` | One-time/short-lived node enrollment grants | `grant_id`, `issued_by_user_id`, `expires_at`, `used_at`, `scope`, `nonce` |
| `cluster_signing_keys` | Route/control token keyring | `kid`, `algorithm`, `key_material_ref`, `status(active/previous/retired)`, `created_at` |
| `cluster_node_metrics` | Latest health/load snapshot per node/org | `node_id`, `organization_id`, `cpu_usage`, `memory_usage`, `active_streams`, `queue_depth`, `reported_at` |
| `resource_ownership_index` | Org-qualified owner resolution | `organization_id`, `kind`, `resource_key`, `owner_node_id`, `owner_server_url`, `updated_at`, `priority` |

### Canonical control message schema (recommended)

`mesh.load.report` envelope fields:

| Field | Type | Notes |
|---|---|---|
| `organizationId` | `string` | Tenant scope |
| `nodeId` | `string` | Reporting node identity |
| `serverUrl` | `string` | Owner endpoint base URL |
| `healthy` | `boolean` | Health gate |
| `metrics.cpuUsage` | `number (0..1)` | Current CPU pressure |
| `metrics.memoryUsage` | `number (0..1)` | Current memory pressure |
| `metrics.activeStreams` | `integer` | Active stream pressure |
| `metrics.queueDepth` | `integer` | Queue pressure |
| `resources[]` | array | Optional ownership hints (`streamKey`, owner flag, priority) |
| `reportedAt` | ISO string | Staleness/TTL filtering |

### Request routing algorithm

For `(organizationId, streamKey)`:

1. Filter nodes by org scope + `healthy=true` + fresh heartbeat.
2. Build candidate set from ownership index + live metrics.
3. Score candidates deterministically (owner bonus + load penalty + error penalty).
4. Apply valid route hint token affinity when possible.
5. If preferred target fails, try next candidate in order.
6. Keep client stream open by proxying upstream SSE response.

### Deployment setup matrix (flexible by scale)

| Setup | Nodes | DNS strategy | LB mode | Data store |
|---|---:|---|---|---|
| Single VPS | 1 | `api.example.com -> node1` | local-only | local DB |
| Small capacity pool | 2-3 | RR/health-checked A records | active-active | shared DB/Redis |
| Multi-AZ | 3-6 | edge LB + regional pools | active-active | shared DB + replicated cache |
| Multi-region | 6+ | geo DNS + regional failover | active-active regional | regional stores + replication strategy |

### DNS canonical patterns

- Public client entrypoint: `api.<domain>`
- Optional regional entrypoints: `api.eu.<domain>`, `api.us.<domain>`
- Internal mesh hostnames: `node-<id>.internal.<domain>`
- Keep short TTL on public failover records (for fast recovery windows).

### Failure behavior

- **Node down before stream start**: candidate fallback before proxy stream opens.
- **Node down during active stream**: proxy emits reconnect event + client reconnects with hint token.
- **LB process restart**: route token remains valid if keyring is shared/persistent.
- **Split-brain risk**: follow mesh partition policy (`T107`) and trust model (`T108`).
