## Ownership boundary

- Database access is API-owned (`apps/api`: each service owns its tables, and the BFF runs the CLI).
- Web consumes data through ORPC contracts and domain hooks.
- Schema and migration lifecycle stays centralized: one schema package, one CLI.

## Canonical locations

- Schema: `packages/nest/schema/src/global/**` (the global Postgres) and `src/local/**` (the node-local SQLite)
- Schema scripts (generate, push, studio): `packages/nest/schema/package.json` (`db:*`)
- Migrate, seed and reset: the BFF CLI, `apps/api/bff/package.json` (`db:migrate`, `db:seed`, `db:reset`)
- Dev entrypoint: `infra/docker/builder/app/entrypoint-app.sh`; prod images run `bun run start` in the app directory (`infra/docker/builder/api/Dockerfile.api.prod`)

## Core commands

```bash
# schema (from packages/nest/schema)
bun run db:generate
bun run db:push
bun run db:studio

# data (from apps/api/bff)
bun run db:migrate
bun run db:seed
bun run db:reset
```

## Runtime order (important)

### Runtime order (dev, compose-managed)

`bun run dev` boots the API container, which runs `entrypoint.dev.ts`
(version → node-startup-check → env validation → diagnostics → `start:dev`).
Migrations and bootstrap happen INSIDE the app lifecycle (orchestrator):

1. Phase 0 (`SetupDevService`) persists the database URL — the compose-managed
   global DB is written to SQLite as `setup_done`, so no wizard appears.
2. The orchestrator runs global Postgres migrations (idempotent).
3. Env-gated default-admin bootstrap:
   - dev (`NODE_ENV !== 'production'`): ensures `DEFAULT_ADMIN_EMAIL` /
     `DEFAULT_ADMIN_PASSWORD` exist when `ENABLE_DEV_BOOTSTRAP` is not
     `false` (default `true`).
   - non-dev: only when `ENABLE_SEEDING=true` (opt-in, default `false`).
4. Main app + web start.

### Production entrypoint

- Migrations run unless `SKIP_MIGRATIONS=true`.
- Admin seeding is opt-in and only runs when `ENABLE_SEEDING=true`.
- Failed migration/seed steps are logged and handled intentionally.

<DocCallout title="Critical rule" tone="warning">
Never perform direct DB access from web code. Keep persistence rules in API services/repositories and expose them through contracts.
</DocCallout>

## Practical workflow

1. Update the schema in `packages/nest/schema/src/global/**`.
2. Generate migration (`db:generate`).
3. Apply migration (`db:migrate` or `db:push` per environment).
4. Update service/repository logic.
5. Update contracts/hooks if response shape changed.
6. Run repository validation (`bun run check`).

## Common pitfalls

- Editing schema and forgetting migration generation.
- Seeding non-deterministic data that breaks repeatability.
- Coupling contract DTOs to DB implementation details.
