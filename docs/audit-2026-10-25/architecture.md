### 2.3 Data ownership
- One Postgres, one schema package `@deployer/nest-schema` (global schema split into `global/{fleet,health,identity,platform,project,runtime,traefik}`), plus a local SQLite (`node_config`, mesh config, cluster node) shared as one file by all six processes.
- Ownership is declared (`packages/nest/schema/src/ownership/table-ownership.ts`, `TABLE_OWNERSHIP` + `SHARED_TABLES` with named single writer + `INFRASTRUCTURE_TABLES`), tested, and lint-enforced per docs. It is a convention, not a boundary: every service connects with the same credentials and the same pool code and can read/write any table. `TableOwner` still has a `"monolith"` member; `health` owns `health_checks`/`health_check_jobs`/`service_health_configs` which `svc-health` never touches.
- The auth tables are written by the BFF (Better Auth) but registered to `identity`.
- Encryption at rest: `encryptedText` columns (dns provider credentials, env var values, webhook secrets, cluster secret material) use AES-256-GCM with a per-row scrypt salt, key = `AUTH_SECRET` (`apps/api-services/shared/src/config/drizzle/schema-codecs.ts`). It is the SAME secret that signs sessions and derives the ingress token; there is no key id/versioning/rotation; `Buffer.from(secret,"hex")` silently accepts non-hex; dev fallback key `scryptSync("temporary-fallback-key")` outside production. Every service holds the key.

### 2.4 Inter-service auth
- Design docs say the BFF forwards an explicit signed Actor claim and services never read the cookie (`ARCHITECTURE.md:159-160`; plan item checked `09-implementation-plan.md:100`). **Reality: the raw browser `cookie`, `authorization` and `x-mesh-internal-key` headers are copied onto each fan-out call** via AsyncLocalStorage (`bff/src/clients/service-auth-context.ts:59-66`, `service-registry.ts:23-28`, `service-auth-context.middleware.ts`). Each service re-validates the session with its own Better Auth instance and a DB lookup (AuthGuard + AuthPlugin both call `getSession`; cookieCache 5 min mitigates). There is no service identity, no service token, no mTLS, no network policy reference. Any caller that can reach `svc-*:310x` on the overlay with a stolen/valid cookie is accepted; any caller with no cookie is rejected, so background/system calls cannot be made.
- Background paths (supervisors, schedulers, webhooks) have no inbound request, hence no credentials, hence cannot call peers (this is why svc-project's fleet call fails, §4).

### 2.5 Migrations
- Canonical journal: `packages/nest/schema/migrations/global/meta/_journal.json`, 40 entries (0000-0039); local SQLite journal 13 entries, applied at module init (`packages/nest/database-local`, WAL + `busy_timeout=15000`).
- `0040_encrypt_environment_variable_values.sql` exists on disk but is **not in the journal** => never applied. Even if applied it only emits a `RAISE WARNING`; the real work is `backfill-env-secrets`, which exists only in the monolith CLI (`apps/api/src/cli/commands/backfill-env-secrets.command.ts`, untracked) and is absent from the BFF CLI that ships in the new images.
- The backfill classifies "already encrypted" as "has exactly four `:`-separated segments" (`looksEncrypted`), so a plaintext value such as `postgres://u:p@h:5432/db` is skipped and then throws on every read.
- Snapshots stop at 0038; 0039/0040 were hand-written (`when: 1792000000000` for 0039). `0010_backfill_service_configs.sql` is also unjournaled (dead).
- `drizzle-kit generate` is configured only in `apps/api/drizzle.config.ts` with `out: ./src/config/drizzle/global/migrations`, i.e. the **stale mirror** (journal ends at `0038_breezy_absorbing_man`, same SQL as canonical `0038_awesome_stature`, different tag), not the canonical package dir the runtime reads. So the documented generation workflow writes to the wrong place, and deleting `apps/api` deletes the only generation toolchain.
- Who applies them at runtime: `BootstrapOrchestratorService.onApplicationBootstrap` in the BFF (`shared/src/core/modules/bootstrap/bootstrap-orchestrator.service.ts:351`) and the setup wizard; `MigrateCommand` in the BFF CLI exits 2 on failure, but the boot path swallows failures (see §4).

## 3. What works end to end (evidence-based)
- Typed oRPC contracts per service, composition per app, procedure surface parity: delegated sets equal implemented sets for the namespaces I diffed (deployment, docker, project, service, domain, user, push, analytics, cluster, nodes, providers, providerSchema, mesh).
- Shared bootstrap order is sound and well documented: build graph -> bind port -> preflight -> exit 5 on missing dependency (`shared/src/server/bootstrap.ts`). `/health` and `/health/ready` are anonymous and correct (`service-health.ts`).
- Cookie propagation works by construction for user-initiated calls; request-scoped ALS prevents cross-request leakage (client cache keyed per contract with per-request headers, `service-client.registry.ts`).
- BFF health roll-up probes every service for real.
- Table-ownership registry + spec exist; auth, entity-level project access rules (`project.entity.ts`) are real and tested.
- Production image can be built for any of the 6 apps with `PRUNE_SCOPE`/`APP_DIR` build args; the bundle keeps `design:paramtypes` (397 occurrences in `apps/api-services/bff/dist/main.js`), so the "bundling breaks Nest DI" rule in `ARCHITECTURE.md:196` is stale.
- Tier scheduling by setup is idempotent and mounts what the supervisors need.
- I did not run the test suites; docs claim 1615 passing across 7 suites and 0 production type errors. Treat as unverified here.

## 4. Broken / risky (ordered by severity)

Critical
1. **Monolith fallback is unbootable**: `@repo/*` imports in `apps/api/src/app.module.ts:18,25,28,69`. The ingress default (`deployer-api`) and shape A therefore point at an app that cannot start. "Roll back to the monolith" is not available today.
2. **Anonymous, ungated setup surface on the public BFF**: `setup.controller.ts:27`. `probeDatabase` opens a connection to a caller-supplied Postgres URL from inside the overlay (internal port-scan/oracle, returns driver error text); `probeMesh` and `remoteAuth` make server-side requests to caller-supplied URLs (`remoteAuth` posts credentials to `${meshOrigin}/api/auth/sign-in/email`); `triggerInitialize` has no `setup_done` guard (`initialization.service.ts:triggerInitialize`, `runInitialize`), and `existingDatabaseUrl` lets the caller repoint the node to another Postgres (the "ensure_empty" step only skips migration/seed, `local-initialization.service.ts:297-314`). I found no post-setup lock on the BFF path (the `SetupGateService` exists only in `apps/setup`). Likely exploitable remotely; UNVERIFIED end to end.
3. **Platform-wide authorization is "logged in", not "allowed"**: `runtime` docker domain (container terminal open/stream, filesystem write/delete/rename, actions run) and `fleet` managed-web (toggle/restart/setOrigin/enableTunnel) and BFF `console.*` require only an authenticated session; any viewer role can exec into containers or repoint the web origin through the BFF. Role gates exist on 10 deployment handlers and 3 reachability handlers only. The BFF delegation layer adds none by design.
4. **Migrations fail open and race**: boot-time migration errors are logged "non-fatal" then `markReady()` (`bootstrap-orchestrator.service.ts:351-358,229`); error matching is by substring ("already"/"duplicate"). Preflight only checks `count(*) > 0` in `drizzle.__drizzle_migrations` (`preflight/checks.ts`), so services pass readiness against a partially migrated schema. No advisory lock; shape C provisions the BFF at 2 replicas and every BFF runs migration + supervisors + default-admin at boot.
5. **Migration 0040 never runs; env-var encryption left half-done**: unjournaled file; backfill command absent from the BFF CLI; shape heuristics in `looksEncrypted` (see §2.5). Existing environments' variables are unreadable after the codec change.
6. **svc-project -> svc-fleet calls are anonymous**: `DnsProviderGateway` uses the shared `ServiceClient` (`shared/src/server/service-client.ts:57`, `createORPCClient(new OpenAPILink(contract,{origin}))`, no headers, no fetch hook) whereas the BFF registry attaches the cookie. Fleet's DNS procedures all `requireAuth()` (`dns-providers.controller.ts`, `cloudflare.controller.ts`), so every project network/zone/record call is a 401 from fleet. Two parallel client stacks (`ServiceClient` vs `@deployer/nest-service-client`) with different auth behaviour.

High
7. **Topology/provisioning incoherence** (shapes A/B/C above): `deployer-bff` vs `svc-bff` names, `platformIngressApiBackend` dead, the stray `provision_api` step creating a mount-less 2-replica BFF with no services behind it.
8. **Image HEALTHCHECK hard-wired to the monolith**: `infra/docker/builder/api/Dockerfile.api.prod:377-381` probes `localhost:3001/health` (BFF is 3005, services 3101-3105) and the tier spec sets `healthcheck: null` (`services-tier-provisioner.service.ts:220`); swarm then inherits an image healthcheck that fails => restart loop (UNVERIFIED which wins, but the spec does not disable it). Image runs as `USER nestjs` while the apps bind-mount `/var/run/docker.sock` and write the shared SQLite/volume; permission outcome UNVERIFIED. Rolling updates have `start-first` with no healthcheck gate to wait on.
9. **Fleet/runtime both host the mesh controller**: `MeshCoreModule` (controllers + in-memory topology, stream registries, health monitor, `StubMeshNodeCaller`) is imported by fleet (`fleet/src/app.module.ts`, `SwarmInventoryModule`) and by runtime (`deployment.module.ts`, docker modules). Two separate mesh runtimes with separate in-memory state in two processes, while the BFF routes only to fleet. `MeshNodeCaller` stub means cross-node resource queries return nothing in both trees.
10. **Multi-node is not designed**: tier has no placement constraints but depends on a node-local named volume (`local.db` holds database URL, mesh secret, node identity) and the node's docker.sock; a task scheduled on a node without that volume has no DB URL. Streams and event buses are in-process (replicas >1 break SSE/streams; `bff` provisioner uses 2 replicas while setup tier explicitly says 1 for that reason). `initializationPromise` and setup event replay buffer are in-memory in the BFF.
11. **Redis is a phantom hard dependency**: `DEPENDENCIES.platform` (BFF, identity, runtime, health) requires `DEPLOYER_REDIS_URL` TCP-reachable (`preflight.service.ts:181-194`) and a Redis supervisor runs it, but no workspace depends on `ioredis`/`redis`/`bull*` and no code uses it (the Bull queues in AGENTS.md do not exist). Readiness is gated on a service nothing uses.
12. **Event outbox does not dispatch**: `LocalEventOutboxDispatcherService.dispatchClaimed` only calls `markSent` (`local-event-outbox-dispatcher.service.ts:125-148`); there is no publisher. The outbox works only as an append-only log read back inside runtime by the projector (in-memory `Map` + in-memory cursor). There is no cross-service event bus, so cross-process realtime depends on shared-DB reads and per-process subjects.
13. **No resilience in the BFF client**: no timeout, retry, circuit breaker or bulkhead on `fetch` in the registry (`service-client.registry.ts`); one slow service hangs every composed screen and each hung leg ties up the request. Errors from a down service surface as generic 500s from delegation handlers. Health roll-up (3 s timeout) is the only timeout in the layer.
14. **Single secret for everything**: `AUTH_SECRET` signs sessions, encrypts columns, derives the ingress token, and is injected as plain env into every swarm service (visible in `docker service inspect`), as are `DEFAULT_ADMIN_PASSWORD` and image tags. No swarm secrets, no rotation.

Medium
15. Contract/doc drift: `ARCHITECTURE.md` (mandates `src/screens/**`, `app.config.ts`, `scripts/build.ts`, `nest-cli.json`, `dto/`, `*.errors.ts` which services lack; says "no bundling"; claims actor claim; lists `configurator`; points to `docs/architecture/04..07` which do exist but describe the same unbuilt pieces), `packages/contracts/AGENTS.md` (paths `apps/api/bff`, `apps/api/services`), `docs/API-CUTOVER-STATUS.md` (test counts disagree internally, blocker 4 is dead code, "0 type errors" retracted then restated).

17. `bff` `test.*` controller and anonymous `/openapi.json` exposed in production; `masterTokenPlugin`/`loginAsPlugin` are enabled purely by env presence (`packages/auth/src/server/auth.ts:185-192`), no production guard.
18. `BaseDatabaseService.isHealthy` calls `execute()` without awaiting (always true for Postgres; unhandled rejection if it fails) (`packages/nest/database-core/src/base-database.service.ts`); only the e2e harness uses it.
19. `seed` in the BFF CLI is a no-op that logs success (`bff/src/cli/commands/seed.command/local.ts`).

## 5. Required for production, in order
1. Decide and freeze ONE topology: delete shape C (`provision_api`/`BffServiceProvisioner`) or make it the only path (then it must mount socket/volumes, schedule svc-*, set `DEPLOYER_API_TARGET`). Delete `platformIngressApiBackend` or wire it. Align names (`svc-bff` vs `deployer-bff`).
2. Close the public attack surface: gate every `setup.*` procedure behind "node not configured" (reject once `setup_done`), restrict `probeDatabase/probeMesh/remoteAuth` targets, make `/openapi.json`, `test.*`, `health.*` and `console.webState` non-anonymous or disable in production.
3. Add platform-role authorization to docker (terminal, filesystem, actions), fleet managed-web, `console.*`; centralise it (one policy, as done for the web in `platform-role.rules.ts`) rather than per-handler.
4. Fix service-to-service auth: one client stack; either forward an Actor claim signed by the BFF and verify it in services, or a service token for background/system calls. Fix `DnsProviderGateway` (it is currently 401). Restrict `svc-*` ports by overlay/network policy.
5. Make migrations safe: journal 0040 (or delete it) and ship `backfill-env-secrets` in the BFF CLI with a real marker instead of the 4-segment heuristic; make boot migration failures fatal; take a `pg_advisory_lock`; make readiness verify "all journal entries applied"; move `drizzle-kit` config/out to `packages/nest/schema`; delete the stale mirror; regenerate snapshots.
6. Fix the images: correct HEALTHCHECK per app (or disable and rely on swarm), non-root vs docker.sock, add a BFF+5 build target to `docker-compose.prod.yml`/CI and publish/tag images the tier provisioner expects (`DEPLOYER_BFF_IMAGE`, `DEPLOYER_SVC_*_IMAGE`).
7. Repair the monolith imports or delete `apps/api` (it cannot boot and keeps three live references: `scripts/verify-mesh-master-decision.ts`, `tooling/vitest` e2e hooks, compose files). If it is going away, port `drizzle.config`, `backfill`, OpenAPI generation first.
8. Pick one home for `MeshCoreModule` (fleet) and route `meshInternal` through the BFF (or document the direct route); replace `StubMeshNodeCaller`.
9. Resolve statefulness for scale: leader election for supervisors/migrations/default admin, sticky or externalised stream/event state, node-affinity for tier or externalise `node_config`.
10. Add BFF client timeouts/retries/circuit breaker and sanitised errors; record swallowed failures in `sections`.
11. Remove or implement Redis; implement real outbox dispatch or rename it to an event log.
12. Tests that matter: BFF contract test for delegated procedures over HTTP (the one that would have caught the mesh and 401 defects), e2e for project/health, a real boot test in swarm.

- Replace 315 generated forwarders by a generic contract-driven proxy router with one auth/policy hook; keep generator output out of the repo.
- Derive per-service Postgres roles from the ownership registry (grant write only to owner) to turn the convention into a boundary; consider schemas per service.
- Key versioning for `encryptedText` (`kid:salt:iv:tag:data`), separate secrets for session, encryption, ingress; use swarm secrets.
- Replace in-memory subjects with Postgres LISTEN/NOTIFY or NATS/Redis streams (finally giving Redis a purpose) so replicas >1 are safe; then run BFF and services at 2 replicas.
- Standardise `ProblemDetails`-style error mapping through delegation; surface upstream status.
- One service catalog consumed by setup, compose, BFF and docs (ports duplicated today in `service-address.ts` and `services-tier-provisioner.service.ts:servicePort`).
- Delete `shared/src/core` duplicates by making `apps/api` go, or make `apps/api` import `@deployer/shared` meanwhile.
- Add the parity script, delegation generator drift check and `bun check --no-script` to CI; fix doc truth (status doc should cite what executes).
