# Deploy / Build / Runtime / Project-model: differentiating features and best-in-class enhancements

Date 2026-10-26. Read-only. Inputs: audit-2026-10-25 (README, deployments, projects-services, docker-cluster, monolith-cutover, bench-market, bench-coolify, bench-dokploy-dockhand) plus direct reads of the code anchors cited below.
All paths relative to `v3/`. Abbreviations: `RT` = `apps/api-services/services/runtime/src/modules`, `FL` = `apps/api-services/services/fleet/src/modules`, `SH` = `apps/api-services/shared/src/core/modules`.

Evidence tags: [bench] = stated in the repo's bench reports (themselves partly [mem]/[search] per bench-market.md section 8); [code] = I read it. Competitor negatives marked "[bench]" are only as reliable as those reports. Nothing here was run.

## 0. Preconditions and a structural warning

1. Everything below assumes the P0 "honest deploy" work from the audit (no `nginx:alpine` fallback, plan persisted on the row, durable queue, swarm runner selectable and default, registry push + digest pull). Several ideas here ARE those fixes done in a more ambitious shape (idea 1 is audit P0 #7 "persist the plan on the row").
2. Where our existing code actually stands (verified):
   - A pure, deterministic config resolver exists with layered scopes mesh -> project -> service -> user, a conditional **dispatch-rule engine** (`when` scope/env/trigger/branch/actorRole/tags -> `apply` patch), computed `constraints` with human-readable `reasons`, and `dispatchAudit.appliedRuleIds` (`SH/configuration/services/configuration-resolver.service.ts:623` resolve, `:217-300` constraints, `:304` matchesRule, `~:900` dispatchAudit). Nothing in the repo persists or edits dispatch rules (I found no producer outside the resolver and its state-machine builder), so it is a powerful but unfed engine.
   - `compilePlan` already builds a plan DAG (source -> build -> deploy -> health, plus preview_name/route_provision/tls_provision nodes and `rollback` edges), hashes it (`planHash` sha256, `compilerVersion`), and has a `/compile-plan/preview` contract (`RT/deployment/services/deployment.service.ts:1194-1290`, `packages/contracts/runtime/modules/deployment/compiler.ts`). Plan snapshots, provenance and execution checkpoints are in-memory `Map`s only (`deployment.service.ts:176-186`, `:1150`), and the executor never reads the plan (deployments.md section 1).
   - The queue payload already carries `executionPlan {builder, runner, runtimeRunnerOptions, customCommands, healthChecks}`, `dependencyGraph`, and `runtimeConfiguration: resolvedRuntimeConfiguration.effective` (`deployment.service.ts:~536-555`). That is 90% of a release manifest; it is simply not persisted. The `deployments` table has `containerImage` (a local tag) and no digest, plan, or config column (`packages/nest/schema/src/global/runtime/deployment.ts:38-114`), although `BuildArtifactResult.artifactDigest` exists (`RT/runners/runtime-runner.interface.ts:7`, workflow `:963`).
   - Five pure fleet services are written and dead: `ServiceDagService` (Kahn layers, cycle detection), `FleetRolloutPlannerService` (modes ordered/parallel/rolling/canary, waves), `FleetReadinessGateService`, `FleetFailureContainmentService`, `FleetRollbackService.decide` (service/project/fleet isolation, reverse dependency order, excludes services without a last-good deployment), plus `DriftReconciliationService` (`FL/fleet/services/*`; injected nowhere per docker-cluster.md 1.2).
   - Routes are a pure function of DB state: newest `success` deployment per service -> ONE `container:port` target (`SH/platform-ingress/services/platform-routes-source.service.ts:~213-277`), rendered as a single-server `loadBalancer` (`lane-traefik-config.ts:93,138`). No weighted or multi-target route exists.
   - Image scanner is real, persisted, cached, and exposes `ensureImageSecurityScan(..., {waitForCompletion})` (`RT/docker/domains/images/security/docker-image-security-scan.service.ts:~52`) plus an auto-scan listener; it is not wired to deploy.
   - Preview-topology dry-run is real and pure: linked-preview, fixed-env, and **mock substitution validated by `implementsContract.contractRef`** (`apps/api-services/services/project/src/modules/service/services/preview-topology.resolver.ts:113-222`). Nothing consumes it. `PreviewEnvOverlayService` is unwired.
   - Mesh CRDT primitives exist: `lww-map`, `or-set`, `hybrid-logical-clock`, `fencing-token` (`SH/mesh/shared/primitives/`), and queue transitions are already best-effort replicated over the mesh (`RT/deployment/queue/deployment-queue-lifecycle.service.ts:~449-467`).
   - Outbox dispatcher only `markSent`s (no publisher) (`SH/events/outbox/local-event-outbox-dispatcher.service.ts`).
   - Swarm runner has real `removeService/scaleService/rollbackService` (`RT/runners/swarm/swarm-runtime-runner.service.ts:69-95`), `deployer.placement` policies (`packages/nest/swarm/src/services/node-placement.service.ts`), but service name embeds the deployment id (`:100-102`) and replicas are hardcoded to 1.
3. **Mesh-first tension (operator principle, MEMORY.md).** Deployments, queue and projects live in Postgres, i.e. a source of truth. Every idea below should make its artefact **content-addressed and signed by the actor's mesh identity** so it can be replicated over the roster/CRDT channel later without redesign. This is cheap now and impossible to retrofit. It is also itself a differentiator: no competitor has a tamper-evident deploy record (they store a jsonb row).

## 1. Brainstorm: 22 candidates

Scoring key: Value (V) / Uniqueness (U) / Feasibility on our code (F), each H/M/L. Effort S <=1 wk, M 1-3 wk, L 3-8 wk, XL >2 months (one engineer, after preconditions).

### 1. Release Manifest + replayable deploy + deterministic rollback with provenance  (V:H U:H F:H) **PICK**
- **User value:** every deployment is a sealed, hash-addressed object "this exact source commit, this image digest, this resolved config, this plan, this scan result, these env var names/hashes". Rollback = re-apply an old manifest (no rebuild, no "latest config"), and you can prove what ran when.
- **Competitors:** Dokploy stores `fullContext` jsonb + image per deployment, registry-backed [bench-dokploy]; Coolify has a `configuration_snapshot` column and retains N images [bench-coolify]; Vercel has instant rollback but is hosted [bench-market]. None, per the bench reports, hash/seal it, tie it to scan result and policy decision, make rollback replay the manifest including config (they roll back the image tag, config stays current), or sign it.
- **Builds on:** queue payload already holds executionPlan + effective runtime config (`deployment.service.ts:~536-555`); planHash + compilerVersion (`:1239-1245`); snapshot contract (`packages/contracts/runtime/modules/deployment/plan-snapshot.ts:28-53`); `artifactDigest` (`workflow:963`); rollback edges (`:1260-1282`); provenance maps (`:1112-1146`); swarm `rollbackService` (`swarm-runtime-runner.service.ts:81`); Dokploy-style rollback is already audit P1 #14/#15.
- **Missing:** a `release_manifests` table (id = sha256 of canonical JSON), manifest builder invoked in `triggerDeployment`, persist-before-enqueue, `deployments.manifest_id` + `image_digest` columns, a replay entrypoint in the worker that skips source/build, env var **values** policy (secrets by reference, never in the manifest), image retention pinned by manifest references (GC must not delete referenced digests), registry digest pull (audit P0 #15).
- **Design sketch:** `Manifest { schema, serviceId, envId, source{repo,sha}, artifact{digest,builder,runner}, effectiveConfig(minus secret values, with secret refs+hash), planHash, scan{digest,summary,at}, policyDecision{gates,appliedRuleIds}, parent(manifestId), actor }`. `deploy(manifestId)` is the only thing the executor accepts; a fresh trigger = build manifest then deploy it. Rollback = `deploy(previous manifestId)` with `--keep-config|--current-config` choice. Rollback edges become real compensation nodes (the edge type already has `compensationNodeId`).
- **Effort:** M-L (L if combined with registry digest pull, which is a precondition anyway).
- **Risks:** secret handling in manifest (hash only, store refs); schema versioning of old manifests; replay of a manifest whose image was pruned (fail loudly, never silently rebuild); storage growth.
- **Feasibility:** high. Most fields already flow through the payload.

### 2. Deploy dry-run ("plan"): exact plan + diff before apply  (V:H U:H F:H) **PICK**
- **User value:** "what will happen if I click deploy" before it happens: builder/runner chosen and why, plan DAG, config diff vs the currently running manifest (env keys added/removed, port, replicas, resources, routes, domains, volumes), gate outcomes (scan, policy, freeze, approval), which services in the graph will cascade, which routes flip, what gets removed. The same output backs a CLI `deployer plan/apply` (bench-market #4, #5).
- **Competitors:** Railway IaC has `config plan`/`apply` for config only [bench-market, [search]]; Komodo Resource Sync shows pending diffs of platform resources, not deploys [bench-market]; Kamal, Dokploy, Coolify, CapRover, Render: no deploy-level plan [bench]. Terraform-style plan for an app deploy including image/scan/route effects is unoccupied.
- **Builds on:** `/compile-plan/preview` contract (`compiler.ts`), pure resolver with `constraints.reasons` and `dispatchAudit` (`configuration-resolver.service.ts:217-300,~900`), `previewTopology` dry-run pattern (project service), `routeVerification` result type, `PlatformRoutesSource` being pure (can be computed against hypothetical state).
- **Missing:** a "simulate" path that runs the same `triggerDeployment` resolution server-side (builder resolution, source resolution, constraint evaluation) without enqueueing; a manifest differ (structural JSON diff with secret masking); a route-diff using the pure routes source over (current rows + hypothetical row); UI/CLI renderers. Requires audit P0 #7 (server-side resolution from the saved service), otherwise the dry-run would show fiction.
- **Design sketch:** `deployment.plan({serviceId, env, ref?}) -> {manifestPreview, diff: [{path, from, to, risk}], gates: [{name, status, reason}], cascade: Wave[], routeChanges, warnings}`. Risk tags: breaking (port change, volume change = data), safe (env add). The apply call takes the planHash and refuses if the world changed (optimistic concurrency, like Terraform's saved plan).
- **Effort:** M (after manifest builder exists, it is the same code run without side effects).
- **Risks:** drift between plan and apply code paths (mitigate: same function with an `effects: false` flag, not a parallel implementation); source resolution needs a network fetch (`git ls-remote`) so a plan can be slow or stale.
- **Feasibility:** high.

### 3. Unified gate engine: scan-gated, policy-gated, approval-gated, window-gated promotion  (V:H U:H F:H) **PICK**
- **User value:** one place that answers "may this manifest enter this environment now?": image scan severity threshold with per-service override, required soak time/health in the lower environment, required approver(s) (project role), allowed time windows, freezes, branch/actor rules, env var policy. Promotion between environments moves the **same digest** (no rebuild) and records who approved.
- **Competitors:** Vercel has per-environment deployment policy + promote [bench-market, [doc]]; Heroku pipelines promote slugs [doc]; Dockhand gates container *updates* on vulnerability thresholds but has no build/promotion [bench-dokploy]; Dokploy/Coolify have no approvals/promotion/freeze (we have `requireApprovalForProduction` as an unenforced setting; Coolify has none) [bench]. Nobody combines scan + approval + window + soak on a digest promotion on self-hosted.
- **Builds on:** `ensureImageSecurityScan({waitForCompletion})`; `environment_promotions` table with `metadata.approvedBy/approvalRequired/rollbackPlan` (`packages/nest/schema/src/global/project/environment.ts:343-368`, unused); resolver `constraints` and dispatch rules (a gate = a `when` condition over context incl. `actorRole`, `branchNameIn`, `requestedEnvironmentIn`, `tagsAll`); `FleetReadinessGateService` (`GateCheckFn`, retry policy) as the soak gate; `requireApprovalForProduction` setting (resolver `~:654`); `github_deployment_rules` table (`fleet/github-provider.ts:123`) already stores per-project rules with priority.
- **Missing:** persistence and UI for dispatch rules/gates (the engine is unfed), a gate result type persisted on the manifest, an approvals inbox + notification (needs the notification system, audit P1 #17), freeze/window policy objects (see 12), promotion service that copies a manifest into a target env with new env-scoped config (requires per-env variables, audit P1 #16).
- **Design sketch:** `Gate = {id, kind: scan|approval|soak|window|rule, params}`, ordered by priority, evaluated into `GateResult[] {status: pass|fail|pending|waived, reason, evidence}` stored on the manifest; a `pending` gate parks the deployment in a new `awaiting_gate` state (resumable, survives restart because it lives on the row, not in memory). Reuse the dispatch-rule syntax so one mental model covers "config by branch" and "policy by branch".
- **Effort:** M for scan+approval+window; L with promotion + UI.
- **Risks:** deadlock UX (nobody approves), scan staleness (use digest + max age), scan DB freshness offline, and the gate must be enforced in the API path not just the UI. Approvals are explicit-permission class: an approval must come from a user in chat/UI, never from observed content.
- **Feasibility:** high; the hard part is persistence + UX, not logic.

### 4. Dependency-graph deploys as a saga: ordered waves, readiness gates, whole-graph rollback  (V:H U:H F:M) **PICK**
- **User value:** deploy "the stack": DB before API before web, each wave waits for the previous to pass health; if a later service fails, roll back the services that were already updated (per failure-isolation policy: service / project / fleet), in reverse dependency order, and tell you exactly what was restored.
- **Competitors:** Coolify/Dokploy deploy resources independently; compose `depends_on` only orders start inside one compose project and does not roll back [bench]; Kamal deploys one app (accessories separate) [bench-market]; Railway/Render have no dependency-aware cascade [bench-market]. v1/v2 of this product had it and v3 lost it (projects-services.md 1.2).
- **Builds on:** `ServiceDagService` (layers, cycles), `FleetRolloutPlannerService` (waves; ordered/parallel/rolling/canary), `FleetReadinessGateService`, `FleetFailureContainmentService`, `FleetRollbackService.decide`, `dependencyGraph` already in the job payload (`deployment.service.ts:~544`), service dependency CRUD with cycle checks (`project/service.service.ts:394-528`), manifests (idea 1) as the rollback unit.
- **Missing:** the orchestrator that connects them (these live in svc-fleet while deployments live in svc-runtime, so it needs a service-to-service call with a signed actor claim; audit architecture #5), a `deployment_run` row (one run -> N deployments) with checkpoint/resume (the in-memory `executionCheckpoints` are the stub), graph UI to add/remove dependencies (none today), `isRequired` semantics in the gate, per-wave timeouts, and the swarm runner as default (rollback of a wave needs `rollbackService` or manifest replay).
- **Design sketch:** `run = plan(DAG) -> for wave in waves: deploy(manifests in wave in parallel) -> gate(readiness of wave) -> on failure: decide(rollback scope) -> replay last-good manifests in reverse order`. A run is idempotent by `runId` and resumable after a restart (checkpoint per wave on the DB row). Partial-failure policies from `DependencyTemplateConfig` (`failureIsolation`, `retryPolicy`) are already typed.
- **Effort:** L. The logic exists; the integration, persistence and UI are the cost.
- **Risks:** cross-service ownership (fleet vs runtime), stateful services (DB rollback is not a manifest replay; mark stateful nodes "never auto-roll-back, require human"), partial rollback leaving schema ahead of code (needs release-phase hooks, see enhancements).
- **Feasibility:** medium-high. Pure logic is done and unit-tested; wiring is the work.

### 5. Canary / weighted rollout at the Traefik layer, with header/cookie targeting and automatic abort  (V:H U:H F:M) **PICK**
- **User value:** send 5% (or a named cohort via header `X-Canary: 1` / cookie) to the new version, auto-promote on healthy metrics over a window, auto-abort on error-rate/latency regression, and flip the route atomically. Works on self-hosted, per service, with no extra mesh product.
- **Competitors:** Vercel Rolling Releases (stages, cookie bucket, abort, API/CLI) is hosted-only [bench-market, [doc]]; Fly has none native [mem]; Dokploy "Zero Downtime" and Kamal-proxy do health-gated cutover, not weighted rollout [bench-market]; Coolify/Dokploy/CapRover/Dokku: none [bench]; Argo Rollouts/Flagger do it on Kubernetes (out of scope).
- **Builds on:** routes are a pure function of state, so a weighted route is "one more row kind" (`platform-routes-source.service.ts:~213-277`); lanes + doors (`lane-traefik-config.ts`); rollout planner already models `canary` with `canaryWeight` and `promotionWindowMinutes` (`fleet-rollout-planner.service.ts:11-18`); `deploymentStrategy` rolling/blue_green/canary is an existing (unconsumed) config value (deployments.md); swarm start-first runner keeps both versions alive; `routeVerification` result already exists.
- **Missing:** multi-target route model (`target` becomes `targets: [{container, port, weight, match?}]`) and a Traefik `weighted` service / header-matched router renderer; a stable swarm service name per (service, env) with a second service per candidate (today each deploy makes a new service with the deployment id in the name, which actually helps canary but needs reaping rules); a metric source for the abort rule (Traefik access log / metrics entrypoint, which the product does not collect, bench-dokploy "Requests page"); sticky-session cookie; state machine for `canary_N%` with abort/promote controls.
- **Design sketch:** stage plan `[5%, 25%, 100%]` with `hold` and `abortIf {errorRate>x, p95>y, healthGate fails}`; route builder emits `weighted` services (Traefik file provider supports it) plus an optional header-matched router for cohort testing; rollback is a weight reset, instant, no restart. Deterministic rule (not an LLM): see bench-market section 7.
- **Effort:** M-L. The routing change is small; metrics ingestion for auto-abort is the long pole (start with health-gate-only abort, add error-rate later).
- **Risks:** WebSocket/session affinity, DB schema compatibility between versions (canary needs expand/contract migrations: document, do not automate), Traefik config churn.
- **Feasibility:** medium; depends on swarm-as-default and a metrics source.

### 6. Ephemeral full-stack preview environments with dependency topology and contract-validated mocks  (V:H U:H F:M) **PICK**
- **User value:** a PR spins up the changed service plus the subgraph it needs; unchanged dependencies are linked to staging/fixed env, replaced by a mock that implements the same contract, or cloned; TTL teardown; URL commented on the PR.
- **Competitors:** Render preview envs copy the whole environment incl. empty datastores with expiry [bench-market, [doc]]; Dokploy previews are single-app, label-gated, max 3 [bench-market]; Coolify previews are per-app with preview-scoped env vars [bench-coolify]; Heroku Review Apps [doc]. None offers per-dependency policy (link/mock/fixed) with a **contract-compatibility check** on the mock (ours: `implementsContract.contractRef` must match).
- **Builds on:** `preview-topology.resolver.ts:113-222` (pure, tested logic), service `preview` config (`backendResolution`, `linkedServices`) saved by the UI (`.../configuration/preview/page.tsx`), `PreviewEnvOverlayService` (unwired, `RT/deployment/preview/preview-env-overlay.service.ts`), preview rows + TTL cleanup (`preview-ttl-cleanup.service.ts`), `compilePlan` preview nodes (preview_name, route_provision, tls_provision), runner type `mock` in vocabulary (no executor), graph saga (idea 4) for ordering/teardown.
- **Missing:** everything in the audit's preview list (real PR build, push/PR webhook resolution fixed, teardown, naming parity create/cleanup), a topology executor that turns resolver output into N deployments, a mock runner (simplest: a generic contract-mock container from an OpenAPI/ORPC contract; start with "mock = another service in the project"), per-preview env overlay (preview-scoped secrets), fork-PR guard.
- **Design sketch:** `previewRun = resolveTopology(PR) -> {changed: build, linked: link env vars to stable URLs, mock: deploy mock service, fixed: pin}`; one DNS wildcard label per run; everything torn down by the run, not by orphan GC. DB branching is idea 7.
- **Effort:** L (depends on real builds, webhooks, run model).
- **Risks:** cost/resource blowup (quota by `maxPreviewEnvironments`, which is inert today), secrets in previews from forks, stale mocks.
- **Feasibility:** medium; resolver is done, execution is not.

### 7. Per-preview database branches / seeded data  (V:M U:H F:L)
- **User value:** previews with realistic data without sharing staging's DB.
- **Competitors:** Render copies datastores empty [bench-market]; Neon-style branching is a hosted DB product, not a PaaS feature (not in the benchmarked set).
- **Builds on:** nothing yet: managed databases and volumes do not exist in v3 (projects-services.md 1.5, bench-market D). Swarm volumes are node-local and named per deployment (docker-cluster.md section 3 #8).
- **Missing:** managed DB service kind, backup engine, volume snapshot (needs LVM/ZFS/btrfs) or `pg_dump | pg_restore` seeding, or `CREATE DATABASE ... TEMPLATE` for Postgres.
- **Effort:** XL. **Feasibility:** low now. Deferred until templates, DBs, and backups exist; then it becomes "restore latest backup into preview DB" which is M.

### 8. Deploy time machine: restore the whole project state at time T  (V:H U:H F:M) **PICK (combined with drift, see 9)**
- **User value:** "put the project back as it was yesterday 14:00": every service re-deployed from its manifest in force at T, config as of T, routes as of T, in dependency order; also a read-only "what was running at T" view for incident review.
- **Competitors:** none self-hosted [bench]; Vercel/Heroku roll back one app; Git-based IaC gives history but not runtime state. Kubernetes GitOps (out of scope) gives it via git.
- **Builds on:** manifests (idea 1) + `deployments` history (every row has status/timestamps) + graph saga (idea 4) + event outbox (for audit timeline) + `environment_access_logs` (schema only).
- **Missing:** **config history** (project/service/environment edits are overwritten in place today; need a `config_revisions` append-only table written by the project service on every mutation, with the same canonical JSON as the manifest), a per-project "state at T" query (join manifests in force per service at T: last `success` before T and not rolled back), route/domain history, and the restore planner = idea 2 (dry-run) + idea 4 (execute).
- **Design sketch:** `projectSnapshot(T) = {services: [{serviceId, manifestId}], envConfigRevisionIds, domainRevisionIds}`; "restore" = compile a run from that snapshot (diff shown first, because it is a plan). Stateful data is out of scope and the UI says so (restores code+config, not data; link to backups when they exist).
- **Effort:** M after ideas 1, 2, 4 (the mostly-new part is `config_revisions`).
- **Risks:** secret rotation between T and now (restoring a manifest that referenced a deleted secret must fail with a clear message), images pruned by GC, migrations that cannot be reversed. All detectable at plan time.
- **Feasibility:** medium-high once manifests exist.

### 9. Drift detection with optional auto-reconcile (desired = manifest, actual = engine)  (V:M-H U:M F:M-H) **PICK (combined with 8)**
- **User value:** know when reality diverged (someone `docker rm`/edited a service, node loss, image changed, label tampering) and either alert or converge back to the in-force manifest.
- **Competitors:** Kubernetes GitOps tools do it; among self-hosted PaaS, none of Coolify/Dokploy/CapRover/Dokku/Dockhand continuously reconcile desired vs actual [bench]; Komodo flags pending **resource-sync** diffs, which is config-as-code, not runtime drift [bench-market].
- **Builds on:** `DriftReconciliationService` (pure diff: deployment_id/image_ref mismatch, never_deployed, failed; severity none/minor/major, `FL/fleet/services/drift-reconciliation.service.ts`), supervisors with reconcile loops (`packages/nest/supervisor-core`, `base-docker-supervisor.service.ts:438 reconcileSwarmService` for platform services), engine labels `deployer.deployment_id/service_id/image_ref` (`swarm-runtime-runner.service.ts:~113-121`), swarm event stream.
- **Missing:** actual-state collector (`docker service ls`/`ps` by label across nodes via mesh), desired-state source (manifest in force), a scheduler, per-environment policy `drift: alert|reconcile|ignore`, and a safety rate limit (no reconcile loops against crash-looping services).
- **Design sketch:** collector emits `ActualState`, diff with `DriftReconciliationService`, policy decides: notify via the (to-be-built) notification system, or `deploy(manifest)` as an ordinary run (so it is gated, logged, and visible, never a hidden side channel). Mesh-first variant: each node reconciles only its own placement from the manifest it holds (needs replicated manifests).
- **Effort:** M. **Risks:** flapping, fighting an operator doing manual maintenance (add a "pause reconcile" lease with TTL, which is a natural LWW-map entry).
- **Feasibility:** medium-high.

### 10. Build cache sharing across mesh nodes  (V:M U:M-H F:L-M)
- **User value:** the second build of a service on any node is fast: layer cache is shared, not per-node.
- **Competitors:** Dokploy "Build Server" and Komodo EC2 builders centralize builds but do not share cache across arbitrary nodes [bench-dokploy]; Coolify has `should_skip_build` and buildx; none documents registry-backed cache over a private mesh [bench].
- **Builds on:** mesh WireGuard overlay (private address space), Docker build via `DockerService.buildImage` (`packages/nest/docker/src/services/docker.service.ts:402-457`; `buildArgs` supported but unused), registry push (precondition).
- **Missing:** the registry itself (audit P0 #11/#15), BuildKit with `--cache-to/--cache-from type=registry`, cache key policy per service/branch, cache pruning, trust model (a cache poisoned by one project must not feed another: scope by project).
- **Effort:** L (the registry is the bulk, but it is a precondition anyway, so marginal cost M). **Risks:** cache poisoning across tenants, disk growth. **Feasibility:** medium.

### 11. Distributed builds on idle mesh nodes  (V:M-H U:H F:M)
- **User value:** builds do not starve the node running your production workload; the platform picks an idle node (or a labelled builder node), builds there, pushes to the registry, deploys by digest.
- **Competitors:** Dokploy build server is a manually configured single remote machine; Coolify `is_build_server` is per-server config; Komodo builders are hosted instances [bench-dokploy, bench-coolify]. Automatic selection by live load across a mesh is not offered.
- **Builds on:** node metrics streams and heartbeat (real data is audit-flagged weak: docker-cluster.md 1.2 "fleet servers", must be fixed first), `NodePlacementService` labels, mesh handlers for remote invocation (docker mesh handler registrar pattern, `docker-mesh-handler-registrar.service.ts`), queue with worker identity and leases (`claimQueueJobs`, `workerId`, heartbeat), build queue in memory today (single serial worker, deployments.md "Queue").
- **Missing:** a build-worker role (builds are claimed by workers on other nodes; the queue lease model already has `workerId`/`lockToken`), registry push, remote build log streaming over the mesh, sandboxing untrusted builds (audit: custom commands run as root alpine, `curl | bash`), concurrency per node, scoring that uses real CPU/mem (not the mislabeled packet-loss numbers).
- **Effort:** L-XL. **Risks:** running untrusted code on non-build nodes (must use a dedicated builder container with no socket, rootless BuildKit); data exfiltration. **Feasibility:** medium; ship after durable queue, registry, and honest node metrics.

### 12. Deploy freezes, maintenance windows, scheduled deploys, enforceable without a central scheduler  (V:M-H U:M-H F:H) fold into gate engine (3)
- **Value:** "no prod deploys Fri 16:00 to Mon 08:00", "deploy at 03:00", emergency override with reason, freeze visible in plan output.
- **Competitors:** Vercel deployment protection [bench-market]; GitHub merge freeze is external; Coolify/Dokploy have none; Render none [bench]. Self-hosted PaaS with freeze: none known [bench-market lists none].
- **Builds on:** gate engine; `lww-map` + `hybrid-logical-clock` so a freeze set on any node is eventually visible everywhere and any node enforces it locally (mesh-first); trigger registry (`SH/triggers`, API/webhook sources) as the single enforcement point.
- **Missing:** policy store (LWW-map entry per scope), timezone-aware window evaluator, override audit (needs audit log), scheduled-deploy trigger source (also fills "no schedule trigger", deployments.md Triggers).
- **Effort:** S-M. **Risks:** clock skew (HLC handles ordering, but windows use wall time: use the platform's configured timezone and node NTP assumption), override abuse (require role + reason + audit).

### 13. Deploy approvals  (V:M U:L F:H) fold into gate engine (3)
Already inert as `requireApprovalForProduction` (resolver `~:654`, project settings). Parity feature, but it becomes differentiating when approval attaches to a *sealed manifest + plan diff* ("approve this exact diff"), preventing time-of-check/time-of-use. Included in idea 3; not separate.

### 14. Per-deployment cost / resource attribution  (V:M U:M-H F:M)
- **Value:** CPU-seconds, memory GB-hours, network, and disk per service/environment/deployment/preview, optionally priced via a per-node cost-per-hour setting ("this PR preview cost 0.04 EUR/day"); finds forgotten previews and oversized services.
- **Competitors:** hosted platforms bill usage; self-hosted peers show live charts only (Dokploy monitoring collector, Coolify Sentinel optional) and none attributes cost to deployments/previews [bench-coolify, bench-dokploy, bench-market J "P3 for self-host: offer resource usage per project instead"].
- **Builds on:** per-container metrics streams, engine labels `deployer.service_id/deployment_id/project_id` on every managed workload (`swarm-runtime-runner.service.ts:~113-121`), node metadata.
- **Missing:** metrics **history** (audit: live streams only, no time series; host metrics misleading) is the blocker; a rollup job; node price config; attribution of shared overhead.
- **Effort:** M (after metrics history, which is itself M). **Risks:** accuracy of metrics (audit flags mislabelled fleet metrics), multi-tenant billing expectations (operator decision single vs multi-tenant). **Feasibility:** medium, gated on metrics store.

### 15. Right-sizing recommendations (auto-sizing from metrics)  (V:M U:M F:M)
- **Value:** "service api: p95 mem 180 MB, limit 1 GB, request 128 MB-> suggested limit 384 MB, saves X"; one click applies it as a plan (dry-run first), never silent.
- **Competitors:** Kubernetes VPA is the reference; no benchmarked PaaS offers it [bench: none listed]. Fly/Render autoscale is horizontal, hosted.
- **Builds on:** metrics history + idea 14 rollup, resolver `resources` (cpuMillicores/memoryMb) and project limit constraints (`configuration-resolver.service.ts:~259`), swarm reservations (currently always `{}`, docker-cluster.md section 1.2: so reservations are a precondition for it to mean anything), dry-run (idea 2) as the apply path.
- **Effort:** S-M after 14. **Risks:** OOM from too-tight suggestions (use p99 + headroom and never auto-apply). **Feasibility:** medium.

### 16. CVE blast radius + scan-triggered redeploy ("which running deployments are exposed to CVE-X?")  (V:H U:H F:H) **PICK (quick win)**
- **User value:** a new CVE lands; one query shows every environment/service/deployment whose in-force digest contains it, with severity and fixed-in version; offer "rebuild with latest base" or "redeploy from patched manifest" through the normal gated pipeline; optional policy auto-opens a rebuild when criticals appear.
- **Competitors:** Dockhand scans images and gates container *updates* by severity, no deployment/environment mapping, no build pipeline [bench-dokploy]; Dokploy/Coolify have no scanning at all [bench]; Portainer scanning is paid [mem]. The scan-to-deployment-to-environment mapping with a remediation path is unoccupied.
- **Builds on:** persisted scan results per image (`DockerImageSecurityRepository`), auto-scan listener (`docker-image-auto-scan-listener.service.ts`), manifest -> digest mapping (idea 1; before that, `deployments.container_image` joined to scan by image id), rescan schedule (the cache max-age already exists, `DEFAULT_IMAGE_SCAN_CACHE_AGE_MS`).
- **Missing:** deployment -> image-digest persistence (blocker is idea 1's `image_digest` column), SBOM/CVE index query, a "rebuild" trigger source in the registry, scheduled rescans, notification delivery.
- **Effort:** S-M. **Risks:** scanner DB freshness, false-positive fatigue (policy thresholds + waivers with expiry), scanner mounts the Docker socket (audit finding; fix before expanding use).

### 17. Verify-before-flip: user-defined smoke gate against the candidate on a private lane, with optional traffic shadowing  (V:M-H U:M-H F:M)
- **Value:** run `curl /healthz && npm run smoke` (a container or HTTP assertion set defined in service config) against the **new** version through a private-lane URL before any user traffic moves; optionally mirror a % of live requests to it and compare status codes.
- **Competitors:** Kamal-proxy/Dokploy/Dokku do readiness checks (container healthy); Heroku release phase runs a command but on the slug, not as traffic verification; none runs a user-defined smoke suite through the real ingress path before the flip [bench-market A, B].
- **Builds on:** health gate + `routeVerification` already verifies Traefik can reach the container (`RT/runners/runtime-runner.interface.ts` result type), lanes (local/private/public) from the platform-ingress design, routes flip only after DB `success` (`platform-routes-source.service.ts:~213`), compile-plan `health` node with a rollback edge (`deployment.service.ts:~1260`). Note the gate today is docker health only and writes "Readiness health gate passed" unconditionally (audit deployments #18): fix that first.
- **Missing:** a per-service `verify` block in config (HTTP assertions first, container command second), a candidate-only route (preview-style host, not the stable label), and the flip step as an explicit node (currently implicit in "success").
- **Effort:** M. **Risks:** side-effecting smoke tests on production data (document read-only), mirroring doubles load/non-idempotent requests (mirroring is opt-in, GET-only default). Traefik supports mirroring services natively.

### 18. Contract-compatibility gate between dependent services  (V:M U:H F:M)
- **Value:** before deploying provider P version N+1, check that every consumer's declared contract (ORPC/OpenAPI ref, `implementsContract.contractRef`) is still satisfied; block or warn with the list of broken consumers.
- **Competitors:** consumer-driven contract testing (Pact) is separate tooling; no PaaS integrates it [bench: none].
- **Builds on:** `implementsContract.contractRef` already stored per service and already used to validate mock swaps (`preview-topology.resolver.ts:199-222`), dependency graph, plan dry-run output.
- **Missing:** contract content (today it is a reference string, not a schema with versions), a diff engine (could reuse the template-version migration/validation ideas in the `template` contract, bench-dokploy section 5 #8), and a place to read the contract from a built artifact.
- **Effort:** L. **Risks:** only as good as authors' contract discipline. **Feasibility:** low-medium; treat as phase 3, after the string ref becomes a versioned schema.

### 19. Deterministic rollback with compensation (migration awareness)  (V:M-H U:M F:M)
Folded into idea 1. A release-phase hook (migrate) marks the manifest `schemaMigrated: true` with an optional `down` command; rollback planning flags "irreversible" and requires explicit confirmation. Rollback edges already model `compensationNodeId`. Competitors: Heroku release phase runs migrations but offers no rollback awareness [bench-market A]. Effort S on top of 1 and pre-deploy command (bench-market quick win #7).

### 20. Preview/stack "sleep" (autostop idle environments) and wake on request  (V:M U:M F:L-M)
Scale preview/staging to zero after idle, wake on first request via a Traefik forward-auth/waker. Fly has autostop/autostart (hosted) [bench-market C]; self-hosted peers none [bench]. Builds on swarm `scaleService(…, 0)` (`swarm-runtime-runner.service.ts:69-95`) and the TTL cleanup timer. Missing: a waker service in the door/ingress, request buffering during cold start, metrics for idleness. Effort M. Cheap resource saver for previews (pairs with idea 6/14).

### 21. Signed, replicated release ledger (mesh-native audit of deployments)  (V:M U:H F:M)
Each manifest and each promotion/approval/rollback is a record signed with the actor's mesh identity key and appended to a replicated log (the roster CRDT machinery: `or-set`, `bounded-event-log`, `fencing-token`). Any node can verify "who deployed what, approved by whom" without Postgres. Competitors: none (bench-market section 5: "signed replicated roster as audit/trust anchor"); Dokploy/Dockhand audit is paywalled and central. Effort M after idea 1. Risks: key custody/rotation (audit: roster token plaintext issues), log growth (bounded log exists). This is the strategic bridge to mesh-first deploys; also enables idea 22.

### 22. Offline-tolerant, node-local convergence (nodes pull their own placement from replicated manifests)  (V:H U:H F:L) **LATER**
Nodes converge on desired state they hold (bench-market section 5, "Edge-local deploys"): a node that was offline catches up without a central scheduler; control-plane loss does not stop reconciliation. Needs manifests replicated (21), placement as data, a swarm-or-not decision (swarm is itself a raft control plane). Effort XL. Do not start before 1, 9, 21 are proven. Included to show the direction the manifest design must not block.

## 2. Selection: best 8, with build order

Ranking criteria: user value x uniqueness (verified against the bench reports) / effort, and whether the prerequisite already exists in code. Ideas that are mostly "wire what is written" rank above ideas needing new infrastructure.

|---|---|---|---|
| 1 | **Release manifest + replay + deterministic rollback** (idea 1, with 19) | M-L | Everything else keys off the manifest. It is also audit P0 #7 and fixes retry/rollback/cancel correctness. Do it as the P0 fix, not as a later feature. |
| 2 | **Deploy dry-run / plan with diff** (idea 2) | M | Same code path with effects off; gives the CLI `plan/apply` and the "what will happen" UX that no competitor has; forces server-side resolution (P0 #7). |
| 3 | **Gate engine: scan + approval + window/freeze + soak, promote by digest** (ideas 3, 12, 13) | M-L | Uses existing scanner, resolver constraints, rules, `environment_promotions`; fixes inert `requireApprovalForProduction`. Persist dispatch rules here, which also unlocks config-by-branch. |
| 4 | **CVE blast radius + rescan-triggered rebuild** (idea 16) | S-M | Cheap, needs only the digest column from step 1 and the existing scanner; strong demo; makes the scanner pay off beyond the Docker page. Can run in parallel with 3. |
| 5 | **Graph saga deploys + whole-graph rollback** (idea 4) | L | Activates five written-but-dead services and restores the v1/v2 cascade promise; needs manifests (1) and the service-to-service actor claim. |
| 6 | **Canary / weighted rollout + verify-before-flip, auto-abort** (ideas 5, 17) | M-L | Requires swarm-as-default and a multi-target route model. Start with health-gate abort and cohort header; add error-rate abort when Traefik metrics are ingested. |
| 7 | **Drift detection/reconcile + project time machine** (ideas 9, 8) | M + M | Both are "manifests in force" queries; reuse plan (2) and saga (5) as the executor; needs config revision history (new append-only table). |

Stretch / next wave: distributed builds + shared cache (10, 11) after registry + honest node metrics; cost attribution + right-sizing (14, 15) after metrics history; contract-compat gate (18); sleep/wake (20); signed release ledger (21) as the mesh-first bridge; node-local convergence (22).

Dependency chain in one line: honest deploy P0 -> **1** -> **2** -> **3** (+**4**) -> **5** -> **6** -> **7** -> **8**.

### Why not different top picks
- Time machine/drift are placed 7th, not earlier, because they have no value before manifests (1) and a reliable executor (5) exist; before that they would show data they cannot act on.
- Canary is 6th, not earlier, because the swarm runner is unreachable today and routes are single-target; shipping canary on the docker runner would be fiction.
- Distributed builds are excluded from the first 8 despite fitting the mesh story: the build pipeline is currently dishonest (no logs, nginx fallback), the registry does not exist, node CPU/memory metrics are mislabelled link metrics (docker-cluster.md 1.2), and untrusted builds need sandboxing. Value is real, timing is wrong.
- Cost attribution is excluded because there is no metrics history, and bench-market J rates usage/cost P3 for self-hosters.

## 3. Cross-cutting design rules for all eight

1. **One executor.** Plan (2), apply, rollback, promote, restore (8), reconcile (9) and preview teardown (6) all become `apply(manifest or run)`. No parallel code paths. This is also what removes the "stored but ignored" bug class (audit cross-cutting #4): a single resolver reads the saved service config.
2. **Rows, not memory.** Runs, gates, approvals, checkpoints live on DB rows (today they are `Map`s: `deployment.service.ts:176-186`, queue lifecycle `:44-45`). Anything that must survive a restart (an `awaiting_gate` deployment, a canary at 25%) is state, not an in-process timer.
3. **Never silent.** Any gate failure, replay failure, missing image, or pruned digest is a visible terminal state with a reason; no fallback to `nginx:alpine` or to "current config" (audit finding 1).
4. **Secrets by reference.** Manifests, plan diffs, approvals and time-machine snapshots store secret names + hashes only; the encrypted `environment_variables` table (unused today) becomes the value store (audit P1 #16).
5. **Authz first.** Every new procedure is gated by the policy layer (audit P0 #5). Approvals/overrides/freezes need an audit-log entry (bench: audit log is S-M and a prerequisite for freeze override accountability).
6. **Content-addressing and signing** as in section 0.3.
7. **Cross-service calls** (fleet <-> runtime <-> project) need the signed actor claim (monolith-cutover.md section 7 #5) before the saga can run unattended; background actors (webhook, schedule, reconcile) need a system actor (audit P0/webhooks).
8. **Duplicate code:** implement in `apps/api-services/*` only. The monolith copy has newer builder/trigger registries that must be ported first (monolith-cutover.md section 3), otherwise the new tier regresses while gaining features.
