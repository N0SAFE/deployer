## 1. Where the project stands (one paragraph)

Not production-ready. Strong foundations (WireGuard mesh with signed roster, pluggable edge providers, setup wizard + handover, Better Auth with passkeys/device flow, typed ORPC contracts, a real Docker-engine UI, 7 runners) sit on top of: authorization that is mostly just "logged in"; several advertised features that are stored-but-inert (webhooks, previews, notifications, cascade deploy, templates, backups, env-var encryption, most project/service settings); a default deploy path that can silently "succeed" with `nginx:alpine`; two diverged backends (monolith `apps/api`, which does not even compile its imports, vs the live `apps/api-services` tier); and no installer, no backups, no green quality gate. Details: README.md §1–§3.

**DECIDED 2026-10-26 — full Effect architecture (supersedes the "hybrid" wording below).** The operator chose to go straight to a **full Effect layer architecture** (services are Effect Layers; Nest shrinks to a thin shell/"islands" during migration), accepted all other DEC-EFF recommendations (recorded in `docs/qa/effect/architecture.md`), and asked for a more granular authN/authZ design. New design docs: [effect-target-architecture.md](effect-target-architecture.md) (layer strata, hosting, oRPC boundary, packaging split, migration order ≈38–46 engineer-weeks, spikes S1–S6), [effect-layers-catalog.md](effect-layers-catalog.md) (49 layers + 22 transformers incl. the `actorOf` replacement, waves Q–4), [authz-authn-design.md](authz-authn-design.md) ("Grants + Guardrails": one `Actor`, typed `resource:action` permissions, grants at platform/project/environment/service/node scope with deny/expiry/conditions, guardrails for step-up/approval/quotas, signed 30-s actor claims, scoped tokens that can only narrow access, shadow-mode rollout; ≈9–12 engineer-weeks to enforced gating). **Quick-win Wave Q** (`ArchiveExtractor`, `CommandRunner`, `SecretBox`+`KeyRing`, `SafeHttp`) closes seven P0 security items on day 1 and needs only `effect-core`.

**Update 2026-10-26 — Effect-TS migration under way.** The operator has started moving services to a hybrid Effect-TS architecture (reference sample `samples/api-sample`, bridge package `packages/nest/effect`; `svc-health` rewritten at the oRPC-procedure level, `svc-identity` mid-rewrite, user domain only). Audit verdict: the design fits (Nest keeps construction/lifecycle, Effect runs handler logic via `@orpc/effect`), but it is a proof of concept, not yet a template — **do not migrate `project`/`fleet`/`runtime` before "Template v1" lands** (`EFF-001`). Known bugs survived the health rewrite (uptime ÷1000, `supervisors: []`). ## 2. How this roadmap is organised

- **One checklist file per area** in [`roadmap/`](roadmap/). Item format (parseable, do not change):
  `- [ ] \`PFX-NNN\` **Title** · FIX|ENHANCE|NEW · P0|P1|P2|P3 · S|M|L|XL · Deps: … · See also: …` + sub-bullets `Why/Problem`, `Do`, `Done when`, `Status · Verified-in-code · Source`.
- **Types:** FIX = something that exists is broken/inert/unsafe · ENHANCE = improve something that works · NEW = does not exist.
- **Priority:** P0 = security/data-loss/correctness blocker before any real use · P1 = makes an advertised feature true / production-necessary · P2 = competitive parity & polish · P3 = nice-to-have/research. **Effort:** S <1d · M 1–3d · L ~1–2w · XL multi-week.
- **Status vocabulary:** `todo | in-progress | blocked(<reason|DEC-id>) | done | obsolete | wontfix`. Box `[x]` = done & validated; `[~]` = obsolete/wontfix (kept, with reason). Items are never deleted or renumbered.
- **Decisions:** `DEC-<AREA>-n` lines at the end of each area file (question · options · recommendation). Open decisions block the items that cite them.

## 3. The four substrates (build once, unlock ~20 items)

Many items depend on these. Each has a **canonical item** (do the work there) and may have an alias item elsewhere — treat them as one piece of work; tick both when done.

| Substrate | What | Canonical item | Alias / related |
|---|---|---|---|
| **SUB-A** | Policy-gated authorization on every ORPC procedure (annotate resource+action+risk, default-deny, shadow-mode → enforce, wire the unused permission engine + `role_rules`, generated 403 test matrix) | `SEC-001` | `IDEA-001`, `SEC-033`, `SEC-038` |
| **SUB-B** | Release manifest: sealed per-deployment record (digest, resolved config, plan+hash, scan, actor) persisted on the deployment row; durable queue; replay/rollback from it | `DEPLOY-003` (foundation) | `IDEA-002` (replay/full), `DEPLOY-001/002/014` |
| **SUB-C** | Event bus with real consumers (outbox dispatch, health `changes$` subscribers) | `OBS-001` | `IDEA-003`, `ARCH-062` |
| **SUB-D** | Capability-scoped roster authority + k-of-n quorum for catastrophic mesh ops | `IDEA-004` | `NET-069`, `NET-076` |

**Effect note:** the recommended implementation vehicle for the substrates is the Effect bridge — SUB-A as an `Actor` service + `Authz` middleware/layers (prototype on three procedures), SUB-B as a Postgres-backed `deployment_jobs` worker with one fiber per job and interruption-based cancel (time-boxed `effect/workflow` spike in parallel), SUB-C as `Stream` consumers over the Postgres outbox with per-consumer cursors, probes via `Schedule`/`Cron`, secrets via `Config.redacted`. The per-request actor/correlation context does not exist yet in the bridge (`EffectRuntime.context()` is process-global) — build it first (`EFF-*`, see effect-migration.md).

Order: SUB-A first (all security + role-aware UI), SUB-B alongside the pipeline fixes, SUB-C before notifications/alerts/audit, SUB-D before more trust is stacked on the roster.
