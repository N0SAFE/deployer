# DB-First Configuration Shift (Mesh + Runtime)

> **Status**: In progress  
> **Started**: 2026-03-31  
> **Scope**: `v3/apps/api` (`drizzle`, `database`, `local-database`, `mesh`, `@repo/env`)  
> **Tracking**: `T274` in `apps/doc/content/docs/deployment/migration-task-breakdown.mdx`

## Why this exists

This document is the persistent execution context for moving runtime/mesh configuration from environment variables to a DB-first model.

Goal: boot with minimal env, complete configuration in-app, and persist operational settings in the correct data plane:

- **Local SQLite**: node-specific and sensitive config.
- **Global Postgres**: cluster-wide policy and shared runtime behavior.

## Problem statement

Current behavior still relies on many `MESH_*` environment variables for runtime behavior and topology defaults, which creates drift and harder operational mutation.

Target behavior:

1. Node can start with minimal env.
2. Node identity/config live in local DB.
3. Shared mesh policy lives in global DB.
4. Mesh reads config from services backed by DB, not from ad-hoc env reads (except strict bootstrap secrets where unavoidable).

## Source plan (full context capture)

Planned work items:

1. Restructure Drizzle layout into shared custom types + global schema/migrations + local schema/migrations; update exports/import paths.
2. Split DB module responsibilities into `GlobalDatabaseService` and `LocalDatabaseService` wiring by consumer.
3. Extend local SQLite schema for node config + sensitive local overrides (encrypted columns).
4. Extend global Postgres schema for cluster-wide mesh policy.
5. Implement `LocalConfigService` and `GlobalConfigService` (read/update APIs + caching).
6. First boot: generate node ID in local DB, initialize defaults, mesh reads DB.
7. Setup-mode flow to configure through app UI/API.
8. Move mesh topology/logic services to DB-backed config services; trim env usage.
9. Remove non-bootstrap mesh env keys from env schema.
10. Make `db:generate`/`db:push`/`db:migrate` support both global + local flows.
11. Keep docs updated in same change sets.

## Decisions already locked

- Local SQLite stores node-specific config and sensitive values (encrypted columns).
- Global Postgres stores shared cluster mesh policy.
- Node ID is generated and persisted in local DB.
- Setup mode remains the path for first-time configuration.

## Status audit (2026-10-07) — what is actually done

Recorded because the plan above is easy to misread as a completion list. Verified
by grepping every read path, not by trusting the plan's ordering.

**Slice 2 is done** (the DB module split): `GlobalDatabaseService` +
`LocalDatabaseService` exist in `core/modules/database/services/`, the legacy
shims are gone, and `DatabaseModule` provides both connections.

**Items 8–9 (mesh topology → DB config, trim mesh env) are PARTIALLY done:**

- Mesh tuning IS owned by a DB-backed service —
  `SystemMeshConfigService` reads/writes `node_mesh_config` in local SQLite and
  seeds its own documented defaults (`DEFAULT_SYNC_INTERVAL_MS`, etc.).
- The env keys that used to shadow it are now **deleted** from `apiEnvSchema`:
  `MESH_SYNC_INTERVAL_MS`, `MESH_PING_SAMPLES`, `MESH_PING_TIMEOUT_MS`,
  `MESH_PEER_MIN`, `MESH_PEER_IMPROVEMENT_THRESHOLD`,
  `MESH_PEER_MAX_REPLACEMENTS`, `MESH_PEER_LATENCY_BUDGET_MS`,
  `MESH_CONTROL_ENVELOPE_TRUST_REQUIRED`, `MESH_TRUST_STRICT_AUTO_ROLLBACK`.
  None had a reader — they were a second, silent place to set a value that had
  no effect. Also deleted for the same reason: `BACKUP_PATH`, `STORAGE_PATH`,
  `SWARM_MAX_TERM_SKEW`, `SWARM_TAKEOVER_MIN_UPTIME_MS`.
- **NOT done — these mesh keys are still read and still env:**
  `MESH_STRICT_REPLAY_GUARD` and `MESH_PEER_MAX` (read via `process.env.X` in
  `mesh-internal-request.service.ts` / `mesh-cluster-sync.service.ts`), plus
  `MESH_TRUST_STRICT_MIN_ACK_RATIO` / `MESH_TRUST_STRICT_MAX_ACK_AGE_SECONDS`
  (read via **computed** `process.env[name]` indexing inside
  `mesh-trust-strict-mode.service.ts`, which is why a naive grep calls them
  dead — they are not). Moving these is the remaining work for item 9.

**Item 4 (cluster-scoped policy in global Postgres) is NOT done.** The stores
exist (`app_config` for `managed_web_app.*`, `github_oauth`), but no cluster-wide
mesh policy has been moved into it.

### Read paths that MUST be checked before deleting any env key

Two independent audits of this file both produced false "dead key" lists. The
misses came from read paths a `env.get("KEY")` grep cannot see:

1. `env.get("KEY")` / `this.env.get("KEY")` — the obvious one.
2. `process.env.KEY` — direct process reads.
3. `process.env[name]` — **computed** indexing. Grep for the literal key finds
   only the string constant, so the key looks unused unless the surrounding
   function is read.
4. `splitManagedEnv()` — reads 39 `MANAGED_*` keys through a **dynamic flat map**
   (`MANAGED_SERVICE_FLAT_KEYS`), so no key name appears at the call site. Every
   `MANAGED_*` key is live by construction.
5. `validateApiEnvPath(value, "KEY")` — schema-path validation; the key is an
   argument, not a property access.

`MESH_TRUST_STRICT_MIN_ACK_RATIO` and `MANAGED_DATABASE_URL` were each wrongly
classified as dead by one of these paths. Verify against source only — build
artifacts under `dist/` and `.next/` contain every generated key name and will
make a dead key look referenced dozens of times.
