Mesh Resource Discovery & Distributed Query System

A zero-boilerplate, fully inferred, strongly typed distributed query and mutation engine over mesh services. Services are distributed schemas. Entities are first-class. Everything composes.

foundation

Introduction & Vision

The mesh layer is no longer modeled as a set of remote procedure calls. It is modeled as a distributed relational execution engine — a collection of services each exposing a typed, queryable, joinable, mutable distributed schema.

❌ Old Model — RPC-Oriented
// Leaks transport concerns to userland
await callMany("deployment:list:req", {
  organizationId: "org-1",
  strategy: "broadcast",
})

// String-based, no type safety
.from(DeploymentMeshService, "list")
✅ New Model — Relational
// Zero transport leakage
const result = await discovery
  .from(DeploymentMeshService
        .entities.deployments.queries.list)
  .where({ status: "running" })
  .execute()
ℹ
Core Mental Shift

Every service is conceptually a distributed database schema. The developer thinks in entities, filters, joins, and mutations — never in topics, request envelopes, or RPC semantics.

03
constraints

Design Principles

Six non-negotiable principles govern every design decision in this system.

  • Services are distributed schemas. A service is a namespace of entities, not a bag of RPCs.
  • Entities are first-class. The primary primitive is MeshEntity, not a topic or handler.
  • Builders are composable and immutable. Every method returns a new builder. Builders can be joined, nested, reused, and streamed.
  • Transport is infrastructure. Users never see topics, envelopes, correlation IDs, or cancellation tokens.
  • No string literals. Operations are always referenced through static typed objects: Service.entities.entity.queries.list — never "list".
  • Everything inferable must be inferred. The developer only declares schemas, item keys, and explicit join predicates. All types derive automatically.
✦
The One Rule

If a developer finds themselves thinking about topics, request shapes, correlation IDs, or transport semantics — the abstraction has failed. Those are exclusively implementation concerns.

primitives

meshOperation() & meshQuery()

The lowest-level primitive. Defines the typed contract of a single distributed operation — its request schema and response schema. Users never touch operations directly; they are wrapped inside entities.

// mesh-operation.ts
export interface MeshOperation<
  TRequestSchema extends ZodType,
  TResponseSchema extends ZodType,
> {
  readonly requestSchema: TRequestSchema;
  readonly responseSchema: TResponseSchema;
}

export function meshOperation<
  TRequestSchema extends ZodType,
  TResponseSchema extends ZodType,
>(
  requestSchema: TRequestSchema,
  responseSchema: TResponseSchema,
): MeshOperation<TRequestSchema, TResponseSchema>
ℹ
Internal Topic Derivation

Every entity operation derives three topics automatically from the namespace and entity key. For example: deployment:deployments:list:req, :res, and :cancel. These are entirely hidden from the caller.

05
primitives

meshEntity()

The primary abstraction. An entity is a distributed queryable and mutable resource. It holds the item schema, the item key used for deduplication, all query operations, all mutation operations, and relation declarations.

export const deployments = meshEntity({
  key: "deployments",

  // The Zod schema for a single item
  item: deploymentSummarySchema,

  // Used for distributed deduplication and join identity
  itemKey: "deploymentId",

  // Query operations: list, resolve, search, etc.
  queries: {
    list: meshOperation(
      z.object({ serviceId: z.string().optional() }),
      z.object({ items: z.array(deploymentSummarySchema) }),
    ),
    resolve: meshOperation(
      z.object({ deploymentId: z.string() }),
      deploymentSummarySchema.nullable(),
    ),
  },

  // Mutation operations: CRUD + domain actions
  mutations: {
    create: meshMutation(...),
    update: meshMutation(...),
    delete: meshMutation(...),
    restart: meshMutation(...),
    scale: meshMutation(...),
  },

  // Declared relations for auto-join inference
  relations: {
    service: meshRelation({
      entity: () => serviceEntity,
      type: "belongs-to",
      on: (deployment, service) =>
        deployment.serviceId === service.serviceId,
    }),
    metrics: meshRelation({
      entity: () => deploymentMetricsEntity,
      type: "has-many",
      on: (deployment, metric) =>
        deployment.deploymentId === metric.deploymentId,
    }),
  },
})

The itemKey field is critical — it drives distributed deduplication across nodes. Multiple nodes may return replicas of the same item; the executor uses this key to merge them with a last-write-wins strategy (extensible to CRDT or vector clocks).

meshMutation()

The mutation counterpart to meshOperation(). Defines the input and result schemas for a distributed write operation.

ℹ
Mutations are not limited to CRUD

Any domain action can be a mutation. restart, scale, promote, drain — all are first-class typed mutations exposed via .invoke("actionName", payload) on the mutation builder.

primitives

meshRelation()

Declares a typed relation between two entities. Relations are the single source of truth for auto-join inference — use .include("relation") on a builder instead of writing an explicit join predicate.

export function meshRelation<
  TSourceItem,
  TRelatedEntity extends AnyMeshEntity,
>(config: {
  entity: () => TRelatedEntity;   // lazy ref to avoid circular deps
  type: MeshRelationType;
  on: (source: TSourceItem, related: EntityItem<TRelatedEntity>) => boolean;
  through?: AnyMeshEntity;           // for many-to-many
}): MeshRelation<TSourceItem, TRelatedEntity>
TypeCardinalityResult shape
belongs-toN:1TRelated | null
has-many1:NTRelated[]
has-one1:1TRelated | null
many-to-manyN:MTRelated[] (via through)

service definition

Service Structure

A mesh service extends BaseMeshService with a namespace and a set of entity definitions. It exposes a static entities object — the entrypoint for all callers.

export class DeploymentMeshService extends BaseMeshService({
  namespace: "deployment",
  entities: {
    deployments,
    deploymentLogs,
    deploymentMetrics,
    deploymentReplicas,
    deploymentEvents,
  },
}) {
  // Static accessor — the only API callers ever use
  static readonly entities = {
    deployments,
    deploymentLogs,
    deploymentMetrics,
    deploymentReplicas,
    deploymentEvents,
  } as const;
}

Callers then reference:

DeploymentMeshService.entities.deployments.queries.list
DeploymentMeshService.entities.deployments.mutations.update
DeploymentMeshService.entities.deploymentLogs.queries.list

No strings. No typos. Full IDE autocomplete. Safe refactors.

⚠
Registration Required

Every mesh service must be registered with the DI container using the multi-token pattern: { provide: MESH_SERVICE_TOKEN, useExisting: DeploymentMeshService, multi: true }. The discovery service collects all registered services at startup.

type system

Complete Type Inference Pipeline

The type system derives everything from the entity definition. The developer only annotates schemas and keys.

Zod Schema
   ↓ inferred item type
meshOperation() / meshMutation()
   ↓ inferred request + response types
meshEntity()
   ↓ item type, operations, relations, mutations
Service.entities.*
   ↓ fully typed static references
Query Builder .from(...)
   ↓ TItem type bound
.join(builder, ...) / .include(relation)
   ↓ join result shape expanded via WithJoin<>
.select({...})
   ↓ projected result type
.execute()
   ↓ Promise<MeshQueryResult<FinalType>>

Key type utility helpers exposed for consumers:

// Extract item type from an entity
type DeploymentItem = EntityItem<typeof deploymentEntity>

// Extract builder result shape
type MyResult = BuilderResult<typeof myBuilder>

// Infer join expansion
type WithService = WithJoin<DeploymentItem, "service", ServiceItem, "left">
// → { deploymentId: string; ...; service: ServiceItem | null }

// Infer aggregate result
type Stats = AggregateResult<typeof myAggSpec>

query layer

Query Builder

The MeshQueryBuilder is the primary consumer API. Obtain one from the discovery service. All methods return a new immutable builder.

// Entry point — always through the discovery service
const query = discovery.from(
  DeploymentMeshService.entities.deployments.queries.list,
)

From here, every builder method is chainable and immutable:

MethodDescription
.where(filter)Apply item-level filters (object or functional form)
.join(builder, config)Join against another builder with explicit predicate
.include(relation)Auto-join via declared relation (no predicate needed)
.select(fields)Project result to a subset of fields
.orderBy(field, dir)Sort the result set
.limit(n)Restrict to n items
.offset(n)Skip the first n items
.aggregate(spec)Compute distributed aggregations
.cache(options)Cache results by fingerprint with TTL and tags
.scope(options)Control distributed execution strategy
.live(options)Return an Observable that re-emits on changes
.stream()Return an async iterator over results as nodes respond
.explain()Return the query plan without executing
.execute()Execute and return a Promise<MeshQueryResult>

Scope & Strategy

The .scope() method controls how the distributed query executes — not which items are returned. It is a transport concern surfaced only when you need fine-grained control.

.scope({
  organizationId: "org-1",
  strategy: "broadcast-merge",
  timeoutMs: 3000,
  broadcastAll: true,
})
broadcast-first broadcast-merge direct-node local-only quorum
11
query layer

Where / Filter System

⚠
Filters Execute Post-Distribution

Where clauses run after all nodes have responded and items have been collected in-memory on the caller. They are not pushed down to individual nodes (see: Invariant I7). This is intentional for the current architecture.

Two filter forms are supported. Both are fully typed — referencing a non-existent field is a compile-time error.

Object form — equality filters, simple and readable:

.where({
  status: "running",
  environment: "prod",
})

Functional form — complex logic with and, or, eq, gt, etc.:

.where(f => and(
  eq(f.status, "running"),
  or(
    eq(f.environment, "prod"),
    eq(f.environment, "staging"),
  ),
))

Select / Projections

Project the result to a subset of fields. The result type narrows automatically — no manual type annotation required.

const result = await discovery
  .from(DeploymentMeshService.entities.deployments.queries.list)
  .select({
    deploymentId: true,
    status: true,
    serviceId: true,

  .execute()

// result.items is inferred as:
// Array<{ deploymentId: string; status: string; serviceId: string }>
13
query layer

Join System

Joins operate exclusively on builders — not on raw services or operation names. This is the fundamental design decision that enables composability.

Basic Join

const activeServices = discovery
  .from(ServiceMeshService.entities.services.queries.list)
  .where({ archived: false })

const result = await discovery
  .from(DeploymentMeshService.entities.deployments.queries.list)
  .join(
    activeServices,
    join => join
      .as("service")
      .on((deployment, service) =>
        deployment.serviceId === service.serviceId,
      ),
  )
  .execute()

Auto-Join via Relations

When a relation is declared on the entity, use .include() to join automatically — no predicate needed:

const result = await discovery
  .from(DeploymentMeshService.entities.deployments.queries.list)
  .include("service")   // auto-resolves join via declared relation
  .include("metrics")  // has-many → result.service.metrics: MetricsItem[]
  .execute()

Nested Joins

A joined builder may itself contain joins, creating an arbitrarily deep distributed relational graph:

const projects = discovery
  .from(ProjectMeshService.entities.projects.queries.list)
  .where({ archived: false })

const services = discovery
  .from(ServiceMeshService.entities.services.queries.list)
  .join(projects, join => join
    .as("project")
    .on((service, project) =>
      service.projectId === project.projectId))

const result = await discovery
  .from(DeploymentMeshService.entities.deployments.queries.list)
  .join(services, join => join
    .as("service")
    .on((deployment, service) =>
      deployment.serviceId === service.serviceId))
  .execute()

// Inferred result type:
// {
//   deploymentId: string
//   serviceId: string
//   service: {
//     serviceId: string
//     projectId: string
//     project: { projectId: string; archived: boolean } | null
//   } | null
// }

Join Type Inference

Join typeDefaultResult shape
leftYesJoined shape becomes T | null
innerNo (.type("inner"))Unmatched rows removed; joined shape is T
✦
Join Execution Model

Cross-service joins execute entirely in-memory on the caller — after all primary distributed queries have completed. There is no distributed query planner. This is intentional: it keeps execution predictable and avoids distributed deadlocks.

query layer

Subqueries & Composable Fragments

Every builder is a first-class object that can be stored, reused, and extended. Builders are immutable — every method returns a new builder without modifying the original.

// Reusable base fragment
const prodDeployments = discovery
  .from(DeploymentMeshService.entities.deployments.queries.list)
  .where({ environment: "prod" })

// Derive specialized builders from the base — immutable
const runningProd = prodDeployments.where({ status: "running" })
const pendingProd = prodDeployments.where({ status: "pending" })
const top10Running = runningProd.limit(10).orderBy("createdAt", "desc")

// prodDeployments is unchanged — safe to reuse in joins
const joined = otherBuilder.join(prodDeployments, ...)

Distributed Aggregation Engine

Aggregations compute in two phases to avoid shipping all raw items over the mesh: partial aggregation on each node, then merge aggregation on the caller (MapReduce pattern).

const stats = await discovery
  .from(DeploymentMeshService.entities.deployments.queries.list)
  .where({ environment: "prod" })
  .aggregate({
    total: count(),
    byStatus: groupBy("status", count()),
    avgReplicas: avg("replicaCount"),
    maxAge: max("createdAt"),
    allEnvs: distinct("environment"),
  })
  .execute()

// Inferred result type (no annotation needed):
// {
//   total: number
//   byStatus: Record<string, number>
//   avgReplicas: number
//   maxAge: string
//   allEnvs: string[]
// }

Available aggregation primitives:

min(field)numberMinimum value of a field

mutation layer

Mutation Strategies & Ownership

Mutation strategies differ from query strategies because writes optimize for ownership and consistency, not discovery.

StrategyBehaviorUse case
owner-routeResolves owning node, routes mutation thereDefault — single authoritative write
broadcastSends mutation to all nodesCache invalidation, distributed notification
quorumWaits for majority acknowledgementConsensus-sensitive writes
local-onlyExecutes only on current nodeLocal state changes
transactionalMulti-step atomic execution (saga)Cross-service coordination
optimisticPatches local cache immediately, syncs asyncReactive UI, low-latency feedback

With owner-route (default), the caller never manually routes. The system resolves entity ownership, determines the authoritative node, and routes transparently:

  1. 1
    Resolve entity keyExtract the itemKey value from the where() clause
  2. 2
    Resolve owner nodeQuery MeshResourceRegistryService for the authoritative node
  3. 3
    Route mutationForward the typed request to the owner node's handler
  4. 4
    Return typed resultUnwrap and validate the response schema
19
mutation layer

Optimistic Mutations

Optimistic mutations immediately apply a patch to the local query cache, then execute the real distributed mutation in the background. On failure, the patch is automatically rolled back.

await mesh
  .from(DeploymentMeshService.entities.deployments)
  .where({ deploymentId: "dep-1" })
  .update({ status: "stopping" })
  .optimistic({
    patch: (current) => ({ ...current, status: "stopping" }),
    onRollback: (original, error) => {
      logger.warn("Optimistic update rolled back", { error })
    },
  })
  .invalidates(["deployments", "prod"])
  .execute()

The optimistic cache (MeshOptimisticCache) stores patches keyed by entity item key. The query executor merges pending patches into query results before returning them. Invariant I15 guarantees rollback always occurs on failure.

mutation layer

Distributed Sagas / Transaction Coordinator

For operations that span multiple services and must be atomic, the saga coordinator provides a declarative step-and-compensate pattern. On failure, compensating actions execute in reverse step order.

const result = await mesh.saga<{ deploymentId: string; routeId: string }>()
  .step("create-deployment", async (ctx) => {
    const r = await mesh
      .from(DeploymentMeshService.entities.deployments)
      .create({ serviceId: "svc-1", environment: "prod" })
      .execute()
    ctx.set("deploymentId", r.result.deploymentId)
  })
  .compensate("create-deployment", async (ctx) => {
    await mesh
      .from(DeploymentMeshService.entities.deployments)
      .where({ deploymentId: ctx.get("deploymentId") })
      .delete()
      .execute()
  })
  .step("create-routing", async (ctx) => {
    return mesh
      .from(RoutingMeshService.entities.routes)
      .create({ deploymentId: ctx.get("deploymentId"), weight: 100 })
      .execute()
  })
  .compensate("create-routing", async (ctx) => {
    await mesh
      .from(RoutingMeshService.entities.routes)
      .where({ deploymentId: ctx.get("deploymentId") })
      .delete()
      .execute()
  })
  .execute()
Step 1 ─success─▶ Step 2 ─success─▶ Step 3 ─FAILURE
                                              │
                            Compensate Step 3 ◀
                            Compensate Step 2
                            Compensate Step 1
                                   ▼
                          SagaRollbackComplete

Reactive Live Queries

.live() returns an Observable<MeshQueryResult<T>> that emits the initial result immediately, then re-emits whenever relevant entity change events arrive on the mesh.

const deployments$ = discovery
  .from(DeploymentMeshService.entities.deployments.queries.list)
  .where({ environment: "prod" })
  .include("service")
  .cache({ ttlMs: 3_000, tags: ["deployments"] })
  .live({ debounceMs: 200 })

deployments$.subscribe(result => {
  console.log("Updated deployments:", result.items)
})
StrategyBehaviorDefault
refetchOnChangeRe-executes the full distributed query on any change eventYes
patchOnChangeApplies item deltas in-memory without a full re-fetchNo

Entity change events are emitted on internal topics: {namespace}:{entity}:changed, :created, :deleted. Services emit these by calling this.emitEntityEvent(...) on BaseMeshService.

Typed Event Subscriptions

Subscribe to specific entity lifecycle events with full type safety. Compose with RxJS operators directly:

mesh
  .on(DeploymentMeshService.entities.deployments)
  .event("updated")
  .where({ environment: "prod" })
  .asObservable()
  .pipe(
    filter(e => e.item.status !== e.previous?.status),

      id: e.item.deploymentId,
      from: e.previous?.status,
      to: e.item.status,

  .subscribe(change => console.log("Status changed:", change))

23
infrastructure

Execution Engine

1. Resolve execution strategy
        ↓
2. Execute primary distributed query across N nodes
        ↓
3. Collect all node responses (with timeout)
        ↓
4. Deduplicate using entity itemKey (last-write-wins)
        ↓
5. Apply where() filters in-memory
        ↓
6. Execute subquery joins in parallel
        ↓
7. Stitch join graph into result shape
        ↓
8. Apply orderBy() clauses
        ↓
9. Apply limit() / offset() pagination
        ↓
10. Apply select() projections
        ↓
11. Run through middleware pipeline
        ↓
12. Return typed MeshQueryResult<T>
ℹ
Joins run in parallel, post-collection

Step 6 executes all joined subqueries concurrently after the primary collection is complete. Cross-service joins never block each other and never block the primary collection.

infrastructure

Distributed Deduplication

Multiple nodes may return the same item (replicas, cached copies, partial sets). The executor deduplicates using the entity's itemKey field.

// In the entity definition:
itemKey: "deploymentId"

// The executor uses this to group identical items and
// resolve conflicts using the configured merge strategy.

Current default strategy: last-write-wins (most recently received item wins). The architecture is designed to accommodate future strategies:

  • Vector clock ordering
  • CRDT merge functions
  • Timestamp arbitration
  • Priority node selection

infrastructure

Query Middleware Pipeline

Cross-cutting concerns are composable middleware applied transparently to every query execution. Registered at module level, never at call site.

// Registration in NestJS module:
MeshModule.forRoot({
  middleware: [
    new MeshTracingMiddleware(tracer),
    new MeshLoggingMiddleware(logger),
    new MeshCircuitBreakerMiddleware({ threshold: 5 }),
    new MeshCacheMiddleware(cacheService),
  ],
})

The middleware interface follows the standard onion/next pattern:

interface MeshQueryMiddleware {
  name: string
  execute<T>(
    context: MeshQueryMiddlewareContext<T>,
    next: () => Promise<MeshQueryResult<T>>,
  ): Promise<MeshQueryResult<T>>
}

Built-in middleware provided by the system:

  • MeshTracingMiddleware — OpenTelemetry span per query
  • MeshLoggingMiddleware — structured query logging with duration
  • MeshCircuitBreakerMiddleware — failure threshold per entity key
  • MeshCacheMiddleware — query fingerprint caching with TTL

Query Caching Layer

Cache results by query fingerprint. Fingerprints encode entity key, where clauses, selected fields, joins, ordering, and pagination. Tag-based invalidation connects cache lifecycle to mutation outcomes.

// Cache on query side:
.cache({ ttlMs: 5_000, tags: ["deployments", "prod"] })

Peer Selection Algorithm

The mesh layer selects peers dynamically based on latency, load, and fleet size. This is the target algorithm — not yet implemented.

⚠

The peer selection algorithm described here is a design hypothesis. Current behavior favors first-seen peers. This section defines the upgrade target.

    Query fleet registryDiscover active nodes from the control plane or mesh discovery service
  2. 2

  3. 3
    Filter candidatesDiscard nodes that fail auth or exceed the failure budget

topology

Scoring & Peer Degree

Candidates are scored on a composite metric. Lower is better (except capacity index C, which is inverted):

Score = w_L·L + w_J·J + w_Q·Q + w_S·S + w_M·M + w_F·F + w_C·(1 − C)
VariableMeaning
LNormalized latency score
JNormalized jitter score
QNormalized queue backlog
SNormalized stream load
MNormalized memory pressure
CNormalized capacity index (higher is better)
FFailure penalty score
w_LLatency weight ≥ 0.35 (weights sum to 1)

The target peer degree k adapts to fleet size and node capacity:

K_base = ⌈a + b·log₂(N)⌉ K_capacity = ⌈K_base · (0.6 + 0.4C)⌉ K_latency = ⌈K_base · (1 − L̃ / L_budget)⌉ k = clamp(minPeers, maxPeers, max(K_base, K_capacity, K_latency))

Defaults: a = 1, b = 2, L_budget = 80ms. Configure all via the mesh module options.

Phase 4 — Hysteresis

To prevent flapping under transient load spikes, the selector applies hysteresis: existing peers are only replaced if a candidate improves the score by at least threshold δ, and at most r peers are replaced per cycle (configurable).

Bootstrap Flows

Flow A — Join Existing Mesh
  • Enter target mesh node URL
  • Enter display name for this node
  • Authenticate as mesh superadmin
  • System connects and registers node
  • Fetch full mesh node URL list
  • Persist URL snapshot in local DB
Flow B — Create New Mesh
  • Create initial local user (superadmin)
  • Enter display name for this node
  • Register as first mesh member
  • Provision local PostgreSQL OR attach existing
  • Persist bootstrap state in local DB

Bootstrap Memory Model

The local database serves as persistent bootstrap memory. It stores:

  • Whether setup has completed
  • Whether the node joined or created a mesh
  • The lifetime asymmetric node identity (public key)
  • The discovered mesh node URL snapshot
  • The last successful mesh state snapshot

On every restart, the orchestration layer reads from this store. If the first peer is unreachable, it continues through the stored URL list until a reachable node is found.

While the mesh is live, any node join or leave event updates the stored URL snapshot so reboots always start from the latest known topology.

Observable-First Mesh API

The mesh call APIs must expose the underlying RxJS Observable stream directly. Aggregation is optional on top.

// Raw stream — compose with any RxJS operator
const stream$ = meshCall.observe()

stream$.pipe(
  map(item => item.deploymentId),
  filter(id => id.startsWith("dep-")),
  take(10),
  scan((acc, id) => [...acc, id], [] as string[]),
  timeout({ each: 5000 }),
).subscribe(...)

// Aggregated result — when you just want the answer
const result = await meshCall.execute()

All standard RxJS operators are valid: map, filter, mergeMap, switchMap, take, scan, combineLatest, timeout, retry, catchError, and everything else in the RxJS toolkit. The goal is to leverage the full power of RxJS for mesh stream composition without artificial limitations.

All System Invariants

These invariants must never be violated. They are the enforceable contracts of the architecture.

  • I1Services expose entities, not raw operations. Users query entities, not topics or RPC calls.
  • I2Everything is strongly typed. Invalid fields, joins, projections, operation references, and aliases are compile-time errors.
  • I3No string operation names. Operations are referenced through static typed objects, never through string literals.
  • I4Builders are immutable. Every builder method returns a new builder. The original is never modified.
  • I5Joins operate on builders only. Joins never accept raw service definitions or operation names.
  • I6Joins are infinitely nestable. A joined builder may itself contain joins.
  • I7Filtering is post-distribution. Where clauses execute after distributed collection, in-memory on the caller.
  • I8Distributed execution is hidden. Users never manage transport, correlation, cancellation, or topology.
  • I9Deduplication is entity-driven. Entities declare itemKey; the executor handles distributed merging.
  • I10Result types are fully inferred. No manual generics, no casts, no DTO duplication.
  • I11Live queries are consistent with last known state. They re-emit on every confirmed entity change event.
  • I12Aggregations execute in two phases. Partial on nodes, merge on caller — no raw item transfer for aggregate-only queries.
  • I13Middleware is composable and order-preserving. Registered order is execution order.
  • I14Relations are the single source of truth for auto-joins. .include() resolves exclusively from declared relations on the entity.
  • I15Optimistic mutations always roll back on failure. The optimistic cache patch is removed and the original state is restored.
  • I16Sagas execute compensating actions in reverse step order. Compensation is deterministic and exhaustive.
  • I17Query plans are always computable without executing. .explain() never triggers a distributed call.
  • I18Event subscriptions are scoped to entity + event type. A subscription never receives events from other entities.
  • I19Cache invalidation is always tag-driven. Never invalidated by raw cache key.
  • I20All capabilities compose with all builder methods. .cache(), .live(), .include(), .aggregate() all work in any combination.
