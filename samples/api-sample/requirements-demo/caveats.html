    Rollout review

    Ten ways this bites a real monorepo

    The requirement model compiles today, but the repo is not the sample. This walks each caveat with a widget you can flip: what the types say, what the runtime does, and where the work actually is.

    Verdict: applicable to apps/api — additive, 6 phases, exports are the cost
    01

    Exports become load-bearing

    The flat Effect context hid every missing import: a controller could yield* any provider in the process. Under Nest visibility, a service is visible to an import only if the providing module exports it. Nothing today depends on that, so the first audit run will light up. The sample now carries a real ConsumerModule: export ReplicaStore too or the root fails with Missing<[DirectoryReaderController, ReplicaStore]>.

    BudgetEvery Missing<[Controller, Service]> is a real dependency. Expect one per controller × service pair the module forgot to export — not a false positive to silence.
    02

    The transitive closure inflates requirements

    RequiredBy is the handler's R, and a service's methods carry their own collaborators. Yielding one domain service drags in its repository, clock and ports. Either the module exports them, or each controller lists the whole chain.

    Rule of thumbInfra modules (Database, Events, Edge, NodeState) go global; domain modules export the services other domains actually use.
    03

    Existing @Global() modules are invisible to the types

    Six modules are global by decorator only. The type side cannot see a decorator, so they look non-global and the audit reports false Missing. Annotating is not optional, and annotating also applies @Global() — a type-only global compiles and then fails at runtime.

    HazardThis is the most likely bad first run: a clean type model reporting failures that are really missing annotations.
    04

    24 call sites pass extra keys positionally

    createModuleContext(metadata, DatabasePort) predates the options argument. Adding { global: true } as the second parameter means either touching those 24 lines or adding a helper that keeps the old shape.

    Cheap either way24 lines is a codemod; a separate createGlobalModule is zero lines. Prefer the helper if you want the migration to stay additive.
    05

    Dynamic modules and re-exports

    The runtime resolves visibility from ModulesContainer, including exports: [SomeModule] chains. forRoot() modules and forwardRef cycles rely on a seen set, not a guarantee — smoke-test with the real graph.

    TestOne integration test per service that boots the real module graph and asserts the controller contexts contain what the types promised.
    06

    The runtime becomes stricter than today

    Today every provider is in one context, so a handler works even when its module never imported the provider. After the switch, the request context is the controller's module context. Anything the types missed — a lie in declareModule, an as any — moves from "works" to 500.

    OrderFlip the runtime per service after its types are green, so the first failure is a compile error, never a 500.
    07

    context() has to survive

    Only the HTTP path becomes per-controller. Seeds, boot code and runPromise callers still need the whole-container context. Deleting it while adding contextFor breaks everything that is not a request.

    Two methods, two jobscontextFor(controller) for requests, context() for everything else. Never merge them back.
    08

    Specs assert a shape that no longer exists

    Controller specs mock EffectContextOf and assert the .use() call; the ORPC host spec calls context() with no argument. They keep compiling, then test the wrong thing.

    Delete, don't patchOnce a controller uses procedure(), the EffectContextOf mock in its spec is dead weight — remove it and assert the procedure type instead.
    09

    Type-check cost moves

    procedure() is a heavier facade than implement(), and ControllerNeeds walks every controller method. The largest controller in the repo has ~40 endpoints — that is where it shows.

    Measure, don't guesstsc --extendedDiagnostics before and after, on svc-project. The numbers below are a model, labelled as such.
    10

    declareModule stays a trust boundary

    A plain module's type does not expose its providers, so provides and exports are claims. Only the collaborators of the claimed services are cross-checked. A lie compiles.

    MitigationRuntime scoping is the backstop: a lie becomes a 500 on first use, not a silent success. Keep the annotations next to the module they describe.
    →

    Rollout plan

    Additive at every step. Modules keep [EffectContextOf] and the flat runtime until their service migrates, so a revert is a file-level change.
